# 取证的判据：怎么证明"真的改了"而不是"看起来成功"

> 手册页 · owner: `skill-author` · 最后核对：2026-11-03
> 本页是 `SKILL.md` §2 第 3A / 第 7 步的展开。**这里是本项目最容易出错的地方。**

## 1. 三级确认（缺一不可，**退出码不作判据**）

任何"改配置"动作做完，必须同时满足三条：

| # | 确认项 | 怎么验 | 为什么不能省 |
|---|---|---|---|
| 1 | **回显** | 逐行确认是 `OK` 不是 `KO` | **必要不充分**：`set ip parameters` 会回 `OK` 却一字未改 |
| 2 | **diff** | `git diff HEAD --numstat -w <工程>/*.ioc` **必须非 0** | 唯一能证明"真的写进去了" |
| 3 | **G1** | 核验器 pass，且 `--expect` 覆盖本次全部外设 | 证明"写进去的东西进了生成物" |

**退出码为什么不算**：CubeMX 退出码**恒为 0**（有 `KO` 也返回 0，D25）。

三级确认能破"全绿幻觉链"（`configure` ok → `.ioc` 没改 → 生成成功 → `MX_GPIO_Init` 本来就在
→ 核验 PASS → 用户以为生效了）。详见 `capability-boundary.md` §5。

## 2. `git status` 与 `git diff` 各自会骗你

| 工具 | 能回答什么 | 局限 |
|---|---|---|
| `git status` | **哪些文件被碰过** | **过度报告**（8 个 vs 实际 2 个） |
| `git diff HEAD --numstat -w` | **哪些有语义改动** | **看不到**仅行尾/缩进的变化 |

**两个工具各自过报/欠报，必须配对使用。**

### 2.1 为什么必须带 `HEAD`

`git diff --numstat -w`（不带基准）比的是**工作区 vs 索引**。S1 流程含 `git add`，
**一旦暂存，它返回 0 个文件**——真实改动被命令自己藏起来。这是"**假干净**"，
比 `git status` 的"假失败"更危险。

```bash
git diff HEAD --numstat -w          # 判据：工作区 vs HEAD
git ls-files --eol <被报 M 的文件>   # 定性：区分 CRLF 噪音与真改动
```

### 2.2 `-w` 的能力边界（别以为它万能）

`-w` 只忽略**空白**差异（行尾、缩进、行内连续空白）：

| 噪音成因 | `--numstat -w` 看得到吗 | 说明 |
|---|---|---|
| CRLF 行尾 | ❌ 看不到 | 这正是我们要的 |
| 仅缩进变化 | ❌ 看不到 | **`-w` 的固有盲区**，可接受（缩进不影响语义） |
| `saveas` 整体重写 | ✅ 看得到 | 行序变化不是空白差异 |
| 版本戳漂移 | ✅ 看得到 | 值变了 |
| 真功能改动 | ✅ 看得到 | — |

⇒ **`numstat -w` 为 0 ⇒ 没有语义改动（可能只有行尾/缩进），不是"没有改动"。**

### 2.3 预置预期：`git status` 会过度报告，这是正常的

按 `* text=auto eol=lf`，工作区是 CRLF、仓库是 LF。**在 `git add` 之前**，
`git status` 会持续把生成文件列成 `M`。⇒ **报 `M` 的文件数 ≠ 改动文件数**，
前者是行尾策略的副作用。**改了一个 GPIO、`git status` 报 8 个 M，是正常的。**

## 3. `.ioc` 大 diff 只有**一个**成因

**版本不匹配导致的迁移重写**（D24.2）：

| 工程 | `.ioc` 版本 | 走了 `saveas` | 实测 diff |
|---|---|---|---|
| G474 模板 | 6.18.1（与锁一致） | 是 | `.ioc` 9/6、`main.c` 11/0 |
| `stm32-digital-clock` | 6.17.0 | 是 | **619/106** |

两者都走 `saveas`，差两个数量级，**唯一变量是版本匹配度**。

**619/106 是 `6.17.0 → 6.18.1` 的观测值，不是阈值、不可跨工程套用**，
一律以当次 `git diff HEAD --numstat` 为准。

判据：

```bash
grep -n "MxCube.Version" <工程>/*.ioc
```

- **版本匹配** → 大 diff 是**异常信号，必须逐条解释**；
- **版本不匹配** → 迁移重写是**预期**，拆独立 `chore(ioc):` 提交，不与功能改动混提交。

## 4. 引脚级落地判据（核验器**默认不查**，必须自查）

核验器默认只保证外设级（`verify-contract.md` §5）；**传 `--expect-pins` + `--ioc` 才会做引脚级断言**
（§4.4），且它只查 `<PIN>.Signal` 与端口时钟使能——**`.ioc` 内部计数/排序仍要自己断言**（D24.3 实测）：

| 断言 | 内容 |
|---|---|
| ✅ | `Mcu.PinsNb == 变更前 + 新增数` |
| ✅ | 存在 `Mcu.Pin\d+=PB0`（本次新增的引脚） |
| ✅ | `Mcu.Pin1..N` 序列**连续无空洞** |
| ❌ | **不要**断言 `Mcu.Pin5=PB0` —— 新增引脚会**插入 `Mcu.Pin1` 位置、原 1–5 整体后移**，这种断言必错 |

这三条属**场景级**断言（S1 的 P1–P4），不是产品保证项——核验器不对"任意工程"校验
`.ioc` 内部计数/排序是否自洽（不同 CubeMX 版本写出的引脚排序本来就可能不同）。

## 5. 汇报 diff 的固定动作

```bash
git diff HEAD --numstat -w
git ls-files --eol <被报 M 的文件>
git diff -- '*.ioc' '*.mxproject' 'scripts/*.mx' 'Core/**'
```

逐条说明改动文件属于哪类：`.ioc`（意图）／`Core/**`（生成物）／`.mxproject`（元数据）／
`Drivers/**`（**不该出现**）。

**必须单独点名**的两种情况：

1. **`USER CODE BEGIN/END` 块之外的改动**——块外用户代码会在下次生成时被覆盖。
2. **`Core/**` 整体重排而非局部增删**——先查 `editor.formatOnSave`（D1），
   那是 clang-format 在保存时重排，与本次意图无关。

出错信号：`Drivers/`、`Makefile`、`startup_*.s`、`*.ld` 出现在 diff 里（这些由 PIO framework 提供）。
