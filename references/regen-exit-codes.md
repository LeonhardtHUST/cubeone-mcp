# `regen.sh` 行为与退出码

> 手册页 · owner: `skill-author` · 以实现为准：`scripts/regen.sh` · 最后核对：2026-11-04
> 本页是 `SKILL.md` §1.5 与 §2 第 0 / 第 4 步的展开。

## 1. 用法

```bash
bash scripts/regen.sh <工程目录> [-e GPIO,TIM4] [-o <证据目录>] [--require-clean] [--fail-fast-on-migrate] [--dry-run] [--skip-generate]
```

它把四件事串成一条：**备份 `.ioc` → 生成 → 核验 → 失败回滚**。

| 选项 | 语义 |
|---|---|
| `-e, --expect <list>` | 期望外设。**可省略**——省略时从 `.ioc` 的 `Mcu.IP*` 自动推导（滤掉 `NVIC/RCC/SYS/DBGMCU` 再补 `GPIO`） |
| `-l, --log <path>` | 生成日志路径（默认 `<out>/cubemx-generate.log`） |
| `-m, --mx <script.mx>` | CubeMX 脚本（默认 `<工程>/scripts/cubemx-generate.mx`） |
| `-o, --out <dir>` | 证据目录。默认 `${TMPDIR:-/tmp}/platform32-regen`，**故意不落在工程里**（避免污染 `git status`）；要入库时显式指到 `docs/logs/phaseN/<场景>/` |
| `--java` / `--cube` | 覆盖解释器/exe 路径 |
| `--timeout <sec>` | **最小 240**（低于自动抬到 240 并告警）；默认 300。单次生成实测约 60 s |
| `--allow-signal <sig>` | 透传给核验器；**默认预置 `VP_RIF_VS_RIF1`**（D8） |
| `--no-default-allow` | 不预置 D8 白名单（严格模式） |
| `--require-clean` | `.ioc` 有未提交**内容**改动时直接退 `2`；**默认允许脏** |
| `--fail-fast-on-migrate` | 前置检查读到 `ProjectManager.AskForMigrate=true` 时**直接退 `2`**，不做生成（**不叠加版本戳判断**）。给 CI / 批处理用，**默认关闭**（默认是分级提示，理由见 §4.1） |
| `--skip-generate` | 跳过生成，只做备份 + 核验（重跑核验用） |
| `--dry-run` | 只打印将执行的命令，不落盘 |

> ⚠️ **自动推导 `-e` 不等于"你本次期望的"**：它是"全量"语义（`.ioc` 里所有 `Mcu.IP*`）。
> 要精确控制就显式传 `-e`，否则漏检/多检都会落到你头上。

> ⚠️ **`--dry-run` 仍会跑前置检查**：`AskForMigrate=true` + 版本戳落后的告警（以及
> `--fail-fast-on-migrate` 的退 `2`）在 `--dry-run` 下**照样触发**——它们发生在
> 备份与生成之前，不属于"将执行的命令"。所以 `--dry-run` 是**不启动 CubeMX 就能看到
> 这条告警**的方法。

## 2. 退出码（`1` 与 `2` 的区别是这条工具最重要的设计）

| 码 | 含义 | 你该做什么 |
|---|---|---|
| `0` | 生成 + 核验通过 | 继续 `pio run` |
| `1` | **跑过了但结果不对**：日志出现整行 `KO`，或核验 FAIL；**已从备份回滚** `.ioc`/`.mxproject` | 看日志与核验报告 |
| `2` | **压根没跑**：前置拒绝或环境错误（`--require-clean` 命中脏 `.ioc`、`--fail-fast-on-migrate` 命中 `AskForMigrate=true`、工程目录不存在、找不到 CubeMX/java、缺 `.mx`、`--expect` 解析失败、**备份 `.ioc` 失败**） | **不要去翻核验报告**——报告根本没生成 |

一句话：**`1` 是"跑了但错了"，`2` 是"没跑"。**

> **W6-2（C7，退出码归一）**：核验器若返回契约外的退出码（`9009` WindowsApps 商店桩、
> `127` 找不到解释器、信号码 `137` 等），`regen.sh` 会**打印原始码并归一为 `2`**，不再把它透传给
> 下游 CI。契约内 `0` / `1` / `2` 原样透传（`1` 前已执行 `rollback_project`）；
> **`{0,1,2}` 是本脚本唯一合法的出口**。实现见 `scripts/regen.sh` 主流程末尾的 `case "$VERIFY_RC"`。

### ⚠️ `2` 还有一个来源：`ioc_backup.py` 的备份完整性校验失败

回滚走 `ioc_backup.py --restore`，而它在还原前会核对 `.ioc.bak` 与旁路摘要 `<name>.ioc.bak.sha256`：

| 情形 | `ioc_backup.py --restore` | `regen.sh` 看到的后果 |
|---|---|---|
| 摘要一致 | 退出码 `0`，原子替换 `.ioc` | 正常回滚 |
| 摘要不一致（篡改 / 部分写入） | 退出码 **`2`** + `[ioc_backup][integrity] 备份疑似被篡改或部分写入：…`，**`.ioc` 一个字节都不动** | 视为"还原失败"，**退化为 `git checkout -- '*.ioc'`**（`rollback_project`） |
| 无旁路摘要（旧版备份） | 退出码 `0` + stdout `[ioc_backup][warn] 缺少完整性摘要（旧版备份），已跳过校验` | 正常回滚，但**这层篡改检测不生效** |

⇒ **`regen.sh` 的退出码 `2` 也可能表示"备份不可信"**，不只是"参数错"。看到 `[ioc_backup][integrity]`
就去查 `.bak` 是怎么坏的（磁盘/同步软件/中途被杀），**不要**把它当成参数问题；此时 `.ioc`
仍是生成后的状态，可先 `git diff` 确认再用 git 回滚。
`regen.sh` 本身只判"非 0 即失败"，没有对 `2` 的专门分支——这是有意的：两种失败的正确续作都是
"别信备份，改用 git"。

## 3. 成功判据是两条，退出码不在其中

```
① 生成日志里没有整行 KO
② 核验器 verdict = pass
```

**为什么不用退出码**：CubeMX **退出码恒为 0**（D25：脚本层回 `KO` 也返回 0）。
实现里用的是整行匹配 `^[[:space:]]*KO[[:space:]]*$`（大写、独占一行）。

### ⚠️ `KO` 判据是**必要不充分**条件

它只能抓"脚本层被 CubeMX 拒绝"（如 `set pin` 写非法信号名）。
**抓不到"命令被静默忽略"**——`set ip parameters …` 会回 `OK`、无 `KO`，却**一字未改** `.ioc`。
脚本自己也会打这行提示：

> 生成阶段：退出码 0 且无 KO。**无 KO 只是必要条件，不是成功证明** ——
> `set ip parameters` 这类命令会回 OK、无 KO，却静默空操作；最终以核验为准。

⇒ **不要让"没 KO"读成"成功了"。** 完整判据见 `diff-evidence.md` 的三级确认。
另注：`KO` 判据是 `regen.sh` 的能力，**手跑 `java -q` 时没有这层保护**。

## 4. `AskForMigrate` 的行为约束（操作纪律，不是建议）

> **`regen.sh` 不修改** `.ioc` 中 `ProjectManager.AskForMigrate` 的值。
> 生成后该值**可能**为 `true`（CubeMX 会写回，见下），**不要在提交前手工复位**——
> 手工复位会让"下次生成到底会不会挂"变成无法追溯的状态。

补充两条事实（**2026-11-04 实测更新**，详见 `references/pitfalls.md` P1）：

- `config save`/`saveas` 会整体重写 `.ioc` 并把该值写成 `true`；**`project generate` 也会把它
  写回 `true`** —— 旧结论"纯 generate 不改写 `.ioc`"**已作废**（实测：置 `false` → 生成一次 →
  读回 `true`；证据 `docs/logs/phase4/12-askformigrate-probe.log`）。
  ⚠️ 生成路径**还可能**因版本迁移改写 `.ioc`（本次实测只动了 2 行版本戳：`6.18.0→6.18.1` /
  `DB.6.0.180→DB.6.0.181`），所以"生成前后 sha256 相同"不能当通用前提。
- `true` + **版本戳低于本机** ⇒ `-q` 生成**会挂死**（实测 300 s 超时，日志停在
  `Begin LoadConfig()`，无 KO、无报错、等一个没人点的模态框；证据
  `docs/logs/phase4/02-first-generate.log`）。把该键置 `false` 后同一脚本 62 s 成功
  （`04-first-generate-retry.log`）。⇒ 拿旧工程生成前**必须先确认它为 `false`**
  （`docs/guides/gate-2.0-checklist.md` §2.1）。

> **为什么不让 `regen.sh` 自动改它**：那是用户工程的既有设置，脚本擅自改会让"我明明关了它"
> 变成不可解释的行为。

### 4.1 生成前的**分级提示**（默认）与 `--fail-fast-on-migrate`（opt-in）

读到 `ProjectManager.AskForMigrate=true` 时，**在调用 CubeMX 之前**按**可判定性**分两级输出
（全程 `stderr`，全程**不改值、不拦跑**）：

| 前置读到的值 | 版本戳 vs 锁定基线 | 默认行为 | 加 `--fail-fast-on-migrate` |
|---|---|---|---|
| `true` | **落后** | **4 行 `[regen][warn]`**：因果一句 + 可复制的置 `false` 命令 + GUI 迁移替代路径 + 指向 P1 | 先打 warn，再**退 `2`**，不启动 CubeMX |
| `true` | 一致 / 更新 | **一行 `[regen]` info**：说明该键为 true 是生成后的**稳态**，但基线是常量、若你机器上的 CubeMX 更新仍可能挂起 | 同样**退 `2`**（开关**不依赖**版本戳判断） |
| `false` | 任意 | **什么都不打**，行为与改动前完全一致 | 同左（开关不生效） |
| 读不到（键缺失 / 文件不可读） | — | 不打印、不改行为（**无法判断时不能凭空告警**） | 同左 |

warn 档的实际输出（可直接复制执行的那一行含**真实绝对路径**）：

```
[regen][warn] AskForMigrate=true 且版本戳 6.18.0 < 基线 6.18.1：无头生成可能停在 Begin LoadConfig() 直到超时（P1）。
[regen][warn]   先关掉该键（可直接复制执行）：python "<repo>/scripts/ioc_field.py" --ioc "<工程>/<名>.ioc" set ProjectManager.AskForMigrate false
[regen][warn]   或用 GUI 打开本工程一次让它完成迁移（会改写 .ioc，需单独提交）。
[regen][warn]   注：基线是常量、不等于你机器上真实安装的版本；判据细节见 references/pitfalls.md P1。
```

#### 为什么分两级，而不是两个极端

`EXPECTED_CUBEMX_VERSION` 是**锁定基线常量**，**不是**"你机器上装了哪个版本"的探测结果。
所以"版本戳落后"只能说"很可能危险"，"版本戳一致"也不等于安全（本机装的可能更新）。

| 方案 | 后果 | 结论 |
|---|---|---|
| **只在落后时输出，一致时完全静默** | 在「工程戳 6.18.1、本机装 6.19.0」这类错配上判"不落后"→ 静默 → **正好漏掉会挂死的那一例** | ❌ 否决：用错的判据换来的安静，比吵闹更危险 |
| **一律 `warn`（不分级）** | `project generate` 每次都把该键写回 `true`（P1-1），于是**每次 regen 都刷 4 行黄字**；用户很快学会无视 `[regen][warn]`——**警告一旦常态化就等于没有警告** | ❌ 否决 |
| **分级（现行）** | 可疑 → `warn`（响亮、带修法）；不确定 → 一行 `info`（低调但不沉默） | ✅ 采纳 |

#### 为什么不直接"见到 `true` 就退 `2`"

停手拒跑需要一个判据，而唯一像样的判据"版本戳是否更旧"**在脚本内不可得**——那需要知道
**当前安装的** CubeMX 版本，不启动它就无从得知。只凭 `AskForMigrate=true` 拒跑，会把
「同版本、能正常生成」的合法工程一并拦下；**误拦的代价高于一次 5 分钟挂起**。

⇒ 默认给**分级提示 + 可复制的修法**，把判断权留在人手里；需要"宁可退 2 也不要挂住"的场景
（CI / 批处理，没人看得见提示）显式加 `--fail-fast-on-migrate`——**该开关只看该键为不为
`true`，不看版本戳**：想安静的场景恰恰最可能挂住，这里不能再用那个不可靠的判据。

> ⚠️ 改动这里的任何一条判据，**必须与 `docs/DECISIONS.md` D36①、`pitfalls.md` P1、本页三处
> 同批修订**，并与 `tests/test_regen_preflight.py` 的三条用例对齐。只改代码会让文档和实现对不上，
> 那比噪音本身更糟。

### 4.2 生成超时（`RC=124`）后的**定向诊断**

超时本身**不是结论**，只是现象。`regen.sh` 在超时分支里检查日志**末行附近**是否停在
`Begin LoadConfig()`，按命中与否给**两种不同**的报告：

| 日志形态 | 判据 | `regen.sh` 的结论 |
|---|---|---|
| 末行附近（尾部 10 个非空行）含 `Begin LoadConfig`，且窗口内**没有** `Change cursor` / `Initializing MCU` / `End LoadConfig` | 就是 P1 的挂死形态（实测：日志 318 行、第 318 行正是 `UtilMem:75 - Begin LoadConfig()`） | 打**定向诊断**："这不是你的工程坏了" + 迁移对话框解释 + **两条处置**（置 `false` 重跑 / GUI 打开一次让它完成迁移）+ 指向 `pitfalls.md` P1 |
| 其他任何形态 | 未命中 | 只报"超时"，并**明确写出"不能归因到迁移对话框"** + 列出该自查的方向 |

为什么不用"整个日志里有没有 `Begin LoadConfig`"：**成功日志里也有这一行**（实测成功日志
638 行，该行在 314，其后还有 324 行）。全文件 grep 会把成功形态也算成挂死。

为什么未命中时要显式说"不能归因"：把所有超时都归给迁移对话框，就变成**"看起来有解释、
其实没解释"**——那比只说"超时了"更坏，因为它会让人停止排查。

> **W6-3（C7）时序更正**：命中 P1 形态时的「定向诊断」打印在 **`rollback_project` 之前**，
> 所以诊断行里**不再宣称「本次已从备份回滚」**（那是时序不实陈述）。回滚是否完成，以随后
> `[regen]` 的「已从 … 恢复 .ioc」日志为准；`die 1` 前一定会执行 `rollback_project`，
> 这个语义没变。W6-3 的负样本用真实日志原文分别覆盖「命中定向诊断」与「不误判」两条分支。

### 4.3 仍然不做的事

`regen.sh` **不修改**该键的值，**不因为**该键为 `true` 而默认拒跑；`--fail-fast-on-migrate`
只影响"跑不跑"，不影响"改不改"。

## 5. 脏工作区语义（1.2.0 起反转）

- **默认允许脏**：失败时从备份恢复 `.ioc`，所以不需要工作区干净。
- `--require-clean` 才严格：`.`ioc` 有未提交内容改动 → 直接退 `2`，**不执行生成**。
- 旧的 `--allow-dirty-ioc` 已删除（两个语义相反的开关并存是陷阱）。
