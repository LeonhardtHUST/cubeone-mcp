## 无 BREAKING

0.7.1 是 **0.7.0 的文档与脚本修正版**：MCP 层与三个 Python 脚本的**行为不变**（唯一例外是 `ioc_field` 的
get 报错文案，见下），`CUBEONE_*` 的语义与 0.7.0 完全一致（`CUBEONE_ALLOWED_ROOTS` 未设 = 拒绝所有路径参数
这条**继续生效**，不因为升到 0.7.1 而放宽）。

从 0.6.x 直接升到 0.7.1 的用户：**迁移步骤照 0.7.0 的说明做**（见 `docs/releases/2026-11-03-v0.7.0.md`），
本版没有新增迁移动作。

## 这个版本改了什么

### ① 注册指南修正：把真正的注册指南放进包里，并对齐 0.7.0 的默认拒绝

0.7.0 的**交付缺口**：默认拒绝上线了，但**没写进任何随包下发的指南**。用户拿到的包里只有
`docs/guides/mcp-registration.md`，而那本讲的是 `vscode-cube-mcp` / `platformio.mcp` 两个**外部 server**，
跟 `npx cubeone-mcp` 怎么注册、`CUBEONE_ALLOWED_ROOTS` 怎么配**毫无关系**；真正讲这些的
`docs/guides/npm-publish-and-codebuddy.md` 当时**没进 `files` 白名单**。结果：用户按包里的指南配完，
0.7.0 的默认拒绝一上来就把所有路径参数拒掉，而包里没有任何一页解释为什么、怎么改。

本版改了三处：

| 位置 | 改了什么 |
|---|---|
| `docs/guides/npm-publish-and-codebuddy.md` | 顶部新增 **0.7.0 BREAKING 区块**（未设白名单 = 全拒、两条出路配白名单/显式 `CUBEONE_ALLOW_NO_ROOTS=1`、`CUBEONE_REQUIRE_ROOTS` 已冗余但保留为 fail-fast）；env 表从 3 行扩到 5 行（补 `CUBEONE_ALLOW_NO_ROOTS` / `CUBEONE_REQUIRE_ROOTS`）；`CUBEONE_ALLOWED_ROOTS` 的口径从"**至少覆盖工程所在盘根，如 `D:\Projects`**"**收紧为**"**只列真正要操作的工程目录；给盘根等于没设防**"（原文是 0.6 时代的话，在 0.7.0 语义下给盘根 ≈ 没设防）；新增 **§2 注册后自检**一节（源码用户跑 `node tools/npm_mcp_handshake.mjs` 期望 12/12 PASS；npm 用户调一次 `ioc_field get MxCube.Version` 读脚注 `allowed_roots=` 三态判读）；反直觉点补第 9 条"注册成功 ≠ 白名单配对了"；文件头加归属说明（本页讲本包，外部 server 见另一本） |
| `docs/guides/mcp-registration.md` | 第一段前加防误读 blockquote：本页讲两个**外部 server**，本包自身的注册见 `npm-publish-and-codebuddy.md`。正文其余不动 |
| `package.json` 的 `files` | 补入 `docs/guides/npm-publish-and-codebuddy.md`。**两本都带**：`mcp-registration.md` 提供双通道背景，`npm-publish-and-codebuddy.md` 是主指南 |

**"注册后自检"为什么必须补**：这是本轮审核发现的最实际缺口——此前用户注册完，**没有任何手段确认
`CUBEONE_ALLOWED_ROOTS` 到底配上没配上**（工具能列出来只证明进程起来了，写错白名单照样列 3 个工具，
只是每次调用被拒）。现在有两条可执行的判定路径，且都能区分"严格有白名单 / 严格无白名单（等于全拒）/
宽松模式"三态。

### ② `ioc_field` 脚本轴 1.0.0 → 1.1.0：get 的报错文案区分「多行歧义」与「键不存在」

0.7.0 的 npm 包里带的 `ioc_field.py` 是 **1.0.0**；master 上是 **1.1.0**（M3 的改动此前未发版）。本版把它带出去：

- `get` 同一个 key 命中**多行**（`.ioc` 里同键重复）时，不再报成"键不存在"，而是明确报**多行歧义**并**附行号**；
- 真正不存在时才报"键不存在"。
- 两者退出码都在域内（`isError=false`），结论看 `structuredContent` 的 JSON —— **调用方不需要改代码**，
  但**排查脚本要按新文案区分这两类**（此前混在一起，会把"文件里有重复键"误读成"这个键没有"）。

脚本轴与包版本轴独立（见 README「三个版本号，别混」）。`verify_generation.py` 仍是 **1.2.0**（7 项 / schema `/2`），
本版未动；`ioc_backup.py` 亦未动。

### ③ 内容边界

- 0.7.1 的代码改动 = **M3 的 5 个未发版 commit**（`ioc_field` 1.1.0、`verify_generation` 弃用口径、README 注记、

- **不含** C1–C4 的任何内容（Windows CI / lock 入库 / 覆盖率 / 硬件预演 / 贡献入口均**未做**，属后续批次）。

## 已知限制

1. **0.7.0 的 npm 包里带的是旧指南，本版起才对。** 已经装了 0.7.0 的用户手里那本
   `mcp-registration.md` 讲的是别的 server，也没提 0.7.0 的默认拒绝——**要么升到 0.7.1，要么直接看仓库里的
   `docs/guides/npm-publish-and-codebuddy.md`**，不要照着 0.7.0 包内那本配。
2. **自检依赖"调用一次工具"**：§2.2 的 npm 用户路径需要客户端能真实发起 `ioc_field` 调用。若客户端只是
   列出工具、调用直接失败在 spawn 阶段（Python 路径问题），脚注不会出现——那属另一类故障，先按
   "无法启动 Python" 处置（设 `CUBEONE_PYTHON`）。
3. **白名单仍不防 TOCTOU**：与 0.7.0 一致，校验通过后、打开文件前链接被替换不在防御范围内。
4. **`CUBEONE_REQUIRE_ROOTS` 冗余未删**：本版只把它在指南里标成"冗余但保留"，没有移除（移除是破坏性变更，
   留待按 D34 的形态变更流程处理）。
5. **npm 包不含 `package-lock.json`**（本仓 `.gitignore:49` 忽略），CI 因此用 `npm install`；lock 入库属 C2 批次。
