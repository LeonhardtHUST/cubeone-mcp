## minor 版：**MCP 输出侧契约增强；输入契约与 7 项判据零改动**

0.8.0 兑现两项遗留增强（PRD E/F 组）：**让 MCP 通道对客户端更可消费**（`outputSchema` +
`structuredContent` 体积上限 + `tail()` 头尾保留）、**对并发更安全**（`ioc_field` / `ioc_backup` 文件锁）。

**没有变的东西（先看这一段）**：

- 工具清单仍是 **3 个**（`verify_generation` / `ioc_backup` / `ioc_field`）；
- **`inputSchema` 的 `required` / `enum` / `additionalProperties` 一字未改**——`tools/list` 的入参契约
  与 0.7.x 完全一致，旧客户端不需要改任何调用代码；
- 核验器仍 **1.2.0**：7 个 `CHECK_*`、`CHECK_ORDER`、schema `platform32.verify_generation/2` 恒定，
  **没有第 8 个 check id**；判定的唯一真源仍是 `verify_documents()`；
- `CUBEONE_*` 环境变量语义、能力边界（只可靠代做普通 GPIO 级改动）不变。

**有三处客户端可感知的行为变化**（都是"新增/更明确"，不是改判据），逐条见下面 ①②③。

## ① `outputSchema`：新增可选字段，旧客户端忽略不报错

三个工具都声明了 `outputSchema`，描述 **`structuredContent` 存在时的形状**（按现有 payload 反推）：

| 工具 | `schema` 常量 | 关键字段 |
|---|---|---|
| `verify_generation` | `platform32.verify_generation/2` | `verdict`（`pass`/`fail`）、`checks[]`（`id`/`status`/`detail`）、`summary`、`inputs` |
| `ioc_backup` | `platform32.ioc_backup/1` | `action`（`backup`/`restore`/`list`）、`project`、`timestamp`、`files[]`（含 `sha256`） |
| `ioc_field` | `platform32.ioc_field/1` | `action`（`get`/`set`）、`ioc`、`key`、`value`/`before`/`after`/`line`/`changed`/`dry_run` |

**兼容性**：

- `outputSchema` 是 **MCP 工具定义里的新增可选字段**。按规范，客户端**忽略未知字段**即不报错；
  旧客户端什么都不做也不会坏。
- 反过来：**读取 `structuredContent` 的消费者应容忍 `outputSchema` 缺失或新增**——不要把它当成
  "字段全集"，也不要因为它存在就认为 `structuredContent` **必然存在**。
- **它也可能没有 `structuredContent`**：执行失败（rc=2 / 进程起不来）或输入错误时只有文本 + `isError`，
  `outputSchema` 描述的是"存在时的形状"，不是"必然存在"。
- **`checks[].id` 的 `enum` 列了 7 个 id，那只是把 F-1 契约显式化**（让客户端能预先知道有哪些检查项），
  **不是第二份判据真源**：某次核验里出现哪些 check、每个 check 是 `pass`/`warn`/`fail`/`skip`，
  仍完全由 `scripts/verify_generation.py` 决定。将来若新增 check id，会**同批**改这里。

## ② `structuredContent` 有 **64 KiB 上限**：超限头尾保留 + `_meta` 告警

**阈值**：`MAX_STRUCTURED_BYTES = 65536`（64 KiB），量的是 `JSON.stringify` 之后的 **UTF-8 字节数**。

**为什么需要**：`verify_generation` 的正常 report < 20 KiB，但 `checks[].detail` 里可能被塞进整段长日志行。
payload 涨到 MiB 级时，客户端要么拒绝、要么在传输层截断——那时 agent 拿到的是"坏 JSON"，
而不是"一个有告警的结论"。

**超限时怎么裁（分级）**：

1. **头部语义字段不裁**：`schema` / `verdict` / `action` / `key` / `project` / `tool` / `summary`（含计数器）；
2. 长字符串**头尾保留**：头 3 072 + 尾 1 024 字符，中间插 `…(截断 N 字符)…`
   （只留尾部会把 `verdict` 与错误前缀吞掉，所以是头尾而不是砍尾）；
3. 长数组保留**前 50 项**；
4. 仍超限 ⇒ 把字符串上限降到 1 024 再跑一遍；
5. 注入 `structuredContent._meta`：

```json
"_meta": {
  "truncated": true,
  "original_bytes": 140384,
  "limit_bytes": 65536,
  "policy": "head-tail-keep",
  "truncated_fields": ["checks[0].detail", "files（数组 80→50）"]
}
```

**未超限时完全不注入 `_meta`** —— 正常返回与 0.7.x **逐字节一致**，不给消费者制造"多了一个字段"的噪音。

**客户端怎么感知**：

- 机读：`structuredContent._meta.truncated === true`；
- 人读：`content[0].text` 末尾追加 `--- 结构化结论已截断（原 N 字节 > 上限 65536）：头部字段（verdict / action / summary …）未裁，被裁字段见 structuredContent._meta.truncated_fields ---`。

> ⚠️ **消费方不得假设 `structuredContent` 永不截断。** 需要完整 `checks[].detail`（比如要把日志行贴进报告）
> 请走 **CLI 通道** 的 `--json-out`：那条路径不经过 MCP 封装层，也就没有这个上限。

## ③ 文件锁：`ioc_field` / `ioc_backup` 的并发写有了明确失败语义

**解决什么**：两个会话同时改同一工程时，`.ioc` / `.ioc.bak` / `ioc-backup.json` 可能互相覆盖
（lost-update，`docs/README.md` §2.1 第 3 条长期登记项）。0.8.0 起写盘前对**工程目录**加排他锁。

| 项 | 值 |
|---|---|
| 锁文件 | `<dir>/.cubeone-lock`（`<dir>` = `.ioc` 所在目录 / `--project` 目录） |
| 互斥范围 | 两个工具**同一把锁** ⇒ 对同一工程互斥 |
| 获取方式 | `os.open(O_CREAT|O_EXCL)`；Win32 映射 `CreateFileW(CREATE_NEW)`、POSIX 是 `open(O_EXCL)`，**原子**且**跨平台同一套代码**（不依赖 `fcntl`，也不用 `msvcrt.locking`） |
| 等待 | `--lock-timeout`，**默认 10s**；`0` = 只尝试一次、立即超时 |
| 锁超时 / 获取失败 | **退出码 2**，stderr `[<tool>][lock-timeout] 无法在 {timeout}s 内获取锁：{lock}（另一进程正在改同一工程？用 --lock-timeout 调大等待）`，**`.ioc` 一个字节都不动** |
| MCP 侧 | 走同一条 `isExecFailure()`：rc=2 ⇒ **`isError=true`**（属"没跑成"，不是"跑完的结论是失败"） |
| 陈旧回收 | 锁文件存活超 **300s** ⇒ 视为陈旧，`os.replace` 改名 `.stale.<ts>` 后删（避免双删竞态） |
| **不加锁**的操作 | `--list`、`get`、`--dry-run`（只读命令不该被写操作排队挡住） |
| 单写者路径 | 零回归：正常路径毫秒级；`regen.sh` 顺序调用（备份 → 生成 → 核验 → 回滚）不受影响 |

**MCP 通道不新增参数**：`inputSchema` 不变，工具内部用默认 10s。要自定义等待时间走 CLI。

> ⚠️ **边界（如实写）**：本锁只覆盖这两个脚本的**进程级**互斥。`regen.sh` 的**跨步骤**并发仍不在范围内
> ——两个 `regen.sh` 同时跑同一工程仍可能互相踩（v0.7.3 起就登记为已知限制，本版**未**解决）。
> 别把这把锁当万能钥匙。

## 同批发版前的两个小修（Q2b）

| 问题 | 症状 | 修法 |
|---|---|---|
| `tools/check_release.py` 的 npm 空输出 | `json.loads(stdout or "{}")` 把"npm 什么都没输出"当成合法空对象 ⇒ **不重试**，并把责任推给 registry（`远端 latest=None ≠ 目标`）——**归因错了** | 解析前判空并**走重试**；两次都空才失败，文案点明「npm view 输出为空」 |
| `lib/server.mjs` 的 `tail()` | `headChars > n` 时 `-(n - headChars)` 变正数，`slice(正数)` 取的是"从第 N 位到末尾"⇒ **上界失效**（实测 `tail(big, 100, 2000)` 输出 20167 字符） | 先把两段预算夹到 `[0, n]`，`tailLen = max(0, n - headChars)` |

这两处都是**判据/裁断行为**的修正，不影响正常路径的返回形态（`tail` 的默认参数下行为不变）。

## 已知限制

1. **仍不防 TOCTOU**：白名单校验通过后、真正打开文件前链接被替换，不在防御范围内（威胁模型是 agent 误操作）。
2. **参数级失明（未修）**：7 项判据看"外设/引脚在不在"，**看不见 `.ioc` 里某个参数被改**（S4 实测 `PLLN 100→85`
   静默改掉 SYSCLK，7 项一条没报）。这类只能靠生成前后 diff 人工过。
3. **T6 在 CI 上恒为 SKIP**：`verify_generation` 那段没有进 CI 的机器判据（缺真实素材）；不造假素材。
4. **日志特征层是"形态校验"不是"语义校验"**：挡的是"随手一份文本"这类**无意**假绿，不是对抗**故意**伪造。
5. **`regen.sh` 的缺参检测只覆盖"选项后无值"**：`--` 之后的位置参数、值以 `-` 开头、`set` 值比较的精确小写
   边界（`TRUE`/`True` 不命中）仍靠人工。
6. **双会话 lost-update：0.8.0 起两个 ioc 脚本有锁，但 `regen.sh` 跨步骤并发仍无锁**——两个 `regen.sh`
   同时跑同一工程仍可能互相覆盖。规避：遵守单写者原则。（这是本版**部分解决**的一条，别读成"已根治"。）
7. **本机工作区仍有 CRLF（`w/crlf` 计数随文档写盘变动，实测在 20–21 之间）**：该计数**不是稳定证据**，
   硬纪律是**发版证据只认 CI 的 LF pack**（见 `docs/README.md` §2.1 第 5 条与台账「发版证据口径」）。
8. **`tools/check_release.py` 仍不挂 CI**：本仓常态是"长期存在未发版改动"，挂进 CI 会每次 push 都红。
9. **F-2 陈旧锁 + `--lock-timeout 0` 的第一次尝试仍会退 2**：`0` 的语义是"只尝试一次"，而"回收陈旧锁 →
   重试"发生在同一轮循环内，所以第一次仍可能直接超时。**这是预期行为**，不是缺陷；后续可优化**文案**
   （提示"锁已陈旧并已回收，请重试"）。登记见 `docs/README.md` §2.1 第 6 条。
10. **F-4 `outputSchema` 里 `_meta` 的声明粒度不一致**：`verify_generation` 展开五个字段，另两个工具只写
    `{type:"object"}`。`_meta` 是可选字段且三处都没有 `additionalProperties:false`，**校验行为等价**，
    属 schema 打磨项。登记同上。

**唯一值得升级的人**：① 会读到 `content[0].text` 首行 `verdict` 的（0.7.4 起 `tail()` 会把它截掉一部分场景，
0.8.0 修好）；② 要被 MCP 客户端自动解析返回结构的（`outputSchema` 让形状可自描述）；③ 曾经被双会话
lost-update 咬过的（现在是明确的 rc=2，而不是静默覆盖）。

npm i -g cubeone-mcp@0.8.0     # 或把 mcp.json 里的版本钉到 0.8.0
