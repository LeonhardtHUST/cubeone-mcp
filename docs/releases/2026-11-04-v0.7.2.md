## 补丁版：**无新增能力**

0.7.2 是 **0.7.1 的补丁版**：MCP 工具清单不变（仍是 `cubemx_*` / `pio_*` / `ioc_*` 那几组）、能力边界不变
（仍只可靠代做普通 GPIO 级改动）、`CUBEONE_*` 语义不变（0.7.0 起的 fail-closed 白名单**继续生效**）、
`verify_generation.py` 版本轴仍是 **1.2.0**（7 项 / schema `/2`）。

**这一版只做两件事：修两个已经在用户手里的缺陷 + 把工程化地基补齐。**
如果你只想知道"要不要升"，答案是：**凡是会在 Windows 控制台直接跑 `scripts/*.py`（CLI 通道）的人，或者
工程里勾选了"为每个外设生成一对 `.c/.h`"的人，都应该升**——前者会拿到退出码 1 的崩溃，后者会被核验器判成
"外设被静默丢弃"的假失败。其余用户升级无感。

从 0.7.1 升到 0.7.2 **没有迁移动作**（不需要改 `mcp.json`、不需要重配白名单）。
唯一需要重读一遍的是**核验器的一处判据语义变更**（`CoupleFile=true` 工程改扫多文件），
它会让同一份工程在 0.7.2 下的 `verdict` 与 0.7.1 不同——**这是修 bug，不是放宽标准**，理由单列一节说明。

## 两处用户可见的缺陷修复

### ① CLI 在非 UTF-8 控制台直接崩溃（脚本退出码 1）

**症状**

在控制台直接跑这三个脚本中的任意一个——

```
python scripts/ioc_backup.py --project <工程目录>
python scripts/ioc_field.py --ioc <工程目录>/board.ioc get MxCube.Version
python scripts/verify_generation.py --log <生成日志> --main-c <工程目录>/Core/Src/main.c \
    --mxproject <工程目录>/.mxproject --expect GPIO --project-root <工程目录>
```

——打印到含 `→` `←` `·` `…` 的那一行抛 `UnicodeEncodeError`，进程以**退出码 1** 结束——
用户看到的是 Python traceback，而**备份/核验其实可能已经做完了**，只有"打印"这一步炸了。

**谁会遇到**

- 在**英文 Windows（控制台代码页 cp1252）**或**旧版中文控制台（cp936）**上，**不经 MCP、直接调脚本**的人
  （即 `SKILL.md` §0.4 说的"CLI 通道"）。这类用户恰恰是"没注册 MCP"的那一半。
- **不受影响**：走 MCP 通道的人——封装层给子进程注入了 `PYTHONIOENCODING=utf-8`，一直没暴露过这个缺陷；
  以及本机代码页本来就是 UTF-8（cp65001）的人——**在本机永远复现不出来**。

> 这个缺陷是**加 Windows CI 当天由第一条 Windows job 打出来的**，不是用户报的。它是"纯本地开发永远发现不了
> 这类缺陷"的第二个实例（第一个是 T3.1 的 `C:/ST/STM32CubeMX/**` 硬编码路径）。

**怎么验证已修**

- **管道/重定向路径**（机器消费，如 `regen.sh` 重定向、MCP 封装层抓管道）：输出被**强制为 UTF-8**。
  `python scripts/ioc_backup.py --project <工程目录> | cat` 得到的是**可读的中文**（不是 `\u7f3a` 这类整体转义），
  退出码 0。
- **TTY 路径**（人读，直接看控制台）：**保留控制台自身编码**（中文 Windows = cp936，中文正常显示），
  只把错误处理换成 `backslashreplace`——cp1252 遇到 `→` 转义成 `\u2192` 而**不再抛异常**。
- 回归守卫：`tests/test_console_encoding.py`（10 例，含"管道编码被污染成 cp1252 时中文仍可读"这条断言），
  以及 CI 的 `windows` job（GitHub Windows runner 控制台就是 cp1252，**这个问题在它上面是必现的**）。

> **为什么不是"把 `→` 换成 `->`"**：改文案只治那一处，下一个脚本加一行中文照样崩。**管道要可解析、
> 控制台要可阅读**，这两件事不能用一条规则通吃，所以按输出目标分流。

### ② 核验器对 `ProjectManager.CoupleFile=true` 的工程**假失败**

**症状**

工程正常生成、`Core/Src/gpio.c` 里定义着 `MX_GPIO_Init`、`__HAL_RCC_GPIOx_CLK_ENABLE()` 也在，`pio run`
也能过——但 `verify_generation.py` 报 **`verdict=FAIL`、`errors=2`**：
`main_init_present` 与 `pins_present` 双双 fail，理由是"`MX_GPIO_Init` 一个定义都没找到"。**配置全对却判失败。**

根因：CubeMX 勾选 *Generate peripheral initialization as a pair of `.c/.h` files per peripheral*
（`.ioc` 里落成 `ProjectManager.CoupleFile=true`）时，`MX_<P>_Init` 被生成到 `Core/Src/<periph>.c`，
`main.c` 里**只有调用、没有定义**；而这两项判据当时只读 `--main-c` 一个文件。

**谁会遇到**

- 用 CubeMX 默认的"每外设一对 `.c/.h`"生成方式的工程——**这是新版 CubeMX 的常见配置**，不是冷门选项；
- 走 `regen.sh` 的人（它自动带 `--project-root`，修复后自动获益）；
- 直调核验器且**没传 `--project-root`** 的人：见下节，这一档仍然拿不到严格判据，但**不再给你一个假的 fail**。

> 这个缺陷是 S4 无板预演（C3）真跑时撞出来的，当时的记录是"判据执行了但结论不可用（L2）"——
> **假失败比漏报更伤人**：用户会去改本来正确的配置。

**怎么验证已修**

- 给 `--project-root`：同一份工程由 `verdict=FAIL errors=2` → **`verdict=PASS errors=0`**，
  且 `main_init_present` 的报错/说明里给出**换算回原文件的行号**，形如 `定义 Core/Src/gpio.c:L42`。
- 未给 `--project-root` **且** `.ioc` 里 `CoupleFile=true`：两项由 fail **降为 warn**，理由写进
  `summary.notes`（原文可见，不静默）。
- **反向守卫**：`CoupleFile=false` 且 `--main-c` 里确实没有定义时**仍然 fail**；
  `tests/test_verify_multifile.py`（7 例）覆盖多文件 pass / 单文件仍 fail / `CoupleFile=true` 降 warn /
  `CoupleFile=false` 不降 / `.ioc` 读取 / 行号换算。
- 既有工程无回归：`_verifier-regen/g474` 仍 `PASS`，仅保留那条预期内的 `mx_script_abs_path` warn。

## 判据语义变更（本版唯一的判据变化）

**改了什么**（`references/verify-contract.md` §4.2 / §4.3 / §4.4 已同步改写）：

| 情形 | 0.7.1 | 0.7.2 |
|---|---|---|
| 给了 `--project-root` | `main_init_present` / `main_init_called` / `pins_present` 只读 `--main-c` | 读 `--project-root` 下 **`Core/Src/*.c`（含 `main.c`）**，命中位置经 `origin_of()` **换算回原文件行号** |
| 没给 `--project-root`，`.ioc` 里 `CoupleFile=true` | fail（假失败） | **降 `warn`** + 理由写进 `summary.notes` |
| 没给 `--project-root`，`CoupleFile=false` / 读不到该键 | fail | **仍 fail**（不受影响） |

**为什么不干脆降级成"永远 warn"**

因为这两项是**非 GPIO 路径上唯一的安全网**。本仓的能力边界说得很清楚：UART / SPI / TIM / ADC 这类外设
**只能手改 `.ioc` 或走 GUI**，而"手改漏了 `IPParameters` 白名单"这种错误**日志干净、什么都不报**
（S3 实测：`MX_TIM4_Init` 出现 0 次、没有任何 `Cannot map`）——**只有 `main_init_present` 能抓住**。
把它变成永远 warn，等于在风险最高的那条路径上**静默废掉检查**：用户会看到一堆"警告"然后学会忽略它们。

所以取值只有一条线：**能读到真相（给了 project-root）就严格判；结构上读不到（无 project-root + 多文件工程）
就如实降级并在 `notes` 里说明**。降级必须**自曝**——和 0.7.0 宽松模式必须回显 `allowed_roots=未设置`
是同一条原则：**能被看见的放宽才叫放宽，静默放宽等于没有放宽可言。**

**这不构成"放宽 7 项标准"**：`log_cannot_map` / `mxproject_abs_path` / `mx_script_abs_path` / `syscalls_path`
四项一字未动，`main_init_called` 的 skip 语义也未动；变的是**"去哪里找定义"**，不是**"找到之后怎么判"**。

## 工程化批次（不改变任何行为，各一句）

- **CI 双平台**：新增 `windows` job（windows-latest，pytest 3.13 + Node 22）——它是 win32 分支（大小写归一 /
  junction / `path.delimiter`）**唯一真跑处**，上线当天就抓出了上面 ① 那个缺陷。
- **`package-lock.json` 入库 + `npm ci`**：依赖装得可复现、`cache: npm` 能命中；此前 lock 被 `.gitignore` 忽略，
  CI 只能用 `npm install`。
- **Python 覆盖率底线**：`--cov=scripts --cov-fail-under=36`（基线实测 37%，取基线 -1pp）——**只防回退、不追指标**；
  这个数字低估真实覆盖面（多数用例用子进程调脚本，子进程内执行不计入 coverage）。Node 侧只出报告、不设门槛。
- **`tools/check_release.py`**：把"`git tag` = `package.json` = `SKILL.md` frontmatter = README 表两处**必须同值**"
  交给机器比，并检查 `docs/releases/` 里有对应正文——人肉对四行在 0.6.2 / 0.7.0 两次发版里都出过前兆。
- **D35 发布 SOP**：9 步流水线成文，含两句"不可交换"的关系与两个已踩过的坑。
- **贡献者文档**：`CONTRIBUTING.md`（三层测试各自的期望尾行、提交文案规范、单写者原则、依赖边界）、
  issue / PR 模板、`docs/README.md` 与 `docs/releases/README.md` 两个索引页。

## 已知限制

1. **仍不防 TOCTOU**：白名单校验通过后、真正打开文件前链接被替换，不在防御范围内。威胁模型是 agent 误操作，
   不是对抗者（与 0.7.0 一致）。
2. **参数级失明（本版未修，且短期修不了）**：7 项判据看的是"外设/引脚在不在"，**看不见 `.ioc` 里某个参数被改**。
   S4 预演实测：重新生成把 `PLLN 100→85`（SYSCLK 推算 200 → 170 MHz）悄悄改掉，**7 项一条都没报**。
   这类改动只能靠 **生成前后 diff 逐条解释**，没有机器判据——接板前必须人工过一遍 diff。
3. **T6 在 CI 上恒为 SKIP**：`verify_generation` 那段没有进 CI 的机器判据（原因见上表）。要覆盖它只能跑
   `--require-materials`（需本机有真实素材），或将来引入一份**脱敏后入库**的完整素材集。
4. **TTY 分支没有自动回归**：`tests/test_console_encoding.py` 覆盖的是**管道**路径（可伪造编码污染）。
   "TTY 保留控制台编码"那半条**只能靠 Windows CI 的真实 cp1252 控制台**间接覆盖——本机代码页是 UTF-8，
   **造不出 cp936 分支**（同 R-B2 的历史注记：这是"验证对象在本机不可达"，不是"纸面修复"）。
