## BREAKING behavior：证据不成立现在退 2，不再"静默放过"

这是本版**唯一**会让既有调用方看到不同结果的变化。它不改判据（仍是 7 项）、不改 schema（仍 `/2`）、
不改 `verdict` 字段含义——**改的是"输入根本不成其为证据"时怎么处置**。

### 0.7.2 及以前：四条路可以拿到假 `pass`

| # | 假绿路径 | 0.7.2 的实际行为 |
|---|---|---|
| A-11 | 只给 `--expect-pins`、**忘了给 `--ioc`** | `pins_present` 判 **skip**，其余 6 项 pass ⇒ `verdict=pass`、rc=0 |
| A-14 | `--project-root` 指错目录 | `mx_script_abs_path` / `syscalls_path` 扫不到东西 ⇒ **skip** ⇒ `verdict=pass` |
| A-17① | `--log` 是一份含**整行 `KO`** 的日志（CubeMX 明确拒绝生成） | 只做 "Cannot map" 文本搜索，**看不见 `KO`** ⇒ `verdict=pass` |
| A-17② + A-4 | `--log` 是**任意文本**甚至是**空文件** | 空文件里没有 "Cannot map" ⇒ `log_cannot_map` **pass** ⇒ `verdict=pass` |

四条路的共同点：**"没查到问题"被当成了"没有问题"**。核验器的输出看起来完全正常——有一个 `verdict: pass`、
7 行 `[pass]`/`[skip]`、退出码 0——而它其实**没有核验任何东西**。

### 0.7.3：证据不成立 ⇒ `rc=2`，且**不落** `--json-out` / `--report-md`

`verify_generation.py` 的 `main()` 里新增一道输入校验 `validate_evidence_inputs()`（**只定义 1 处、只在
`main()` 调用 1 处**），四条判据一一对应上表：

1. `--expect-pins` 已给但未给 `--ioc` ⇒ 退 2；
2. `--project-root` 已给但其下 `Core/Src/*.c` 一个都没有 ⇒ 退 2（指错目录）；
3. `--log` 是空文件（0 字节）或只有空白 ⇒ 退 2；
4. `--log` 内容**命中不到 2 类** CubeMX 日志特征 ⇒ 退 2（不是 CubeMX 日志）。

**关键点：证据不成立时不产出任何报告文件。** 0.7.2 的坏处不只是 rc=0，而是它会**写出一份 `verify.json`**
落进 `docs/logs/`，让后面所有"看 JSON 说话"的环节（报告、看板、发版门禁）继续引用一份空证据。
0.7.3 在这种情况下**一个字节都不写**，`--json-out` / `--report-md` 指定的路径保持不存在。

而**"整行 `KO`"**（A-17①）走的是另一条路：它**不是输入错误**，而是**生成阶段真的失败了**，所以复用既有的
`log_cannot_map` 判据判 **FAIL**、`rc=1`——不新增 check id、不改 `CHECK_ORDER`，只在 `check_log_cannot_map()`
里加一次 `KO` 行扫描：

```
[fail] log_cannot_map  生成脚本被 CubeMX 拒绝（命中 2 行整行 'KO'）：L18: KO；L19: KO；
                       属生成阶段失败，须回滚并核对 .ioc / GUI 配置（D25：CubeMX 退出码恒为 0）
```

> **为什么退 2 而不是退 1**：`1` 是"跑完了，结论是 fail"，`2` 是"压根没跑成，没有结论"。
> 把"没有结论"报成"结论是 fail"，用户会去查外设配置；报成"结论是 pass"，用户会直接发版。
> 两种都是**归因错误**。`SKILL.md` §0.4 与 `references/verify-contract.md` 的退出码表一直是这个三分法，
> 0.7.3 只是把核验器自己遵守它。

### 谁会看到变化 / 迁移提示

- **CLI 通道（直接跑脚本）**：脚本**早就**在 help 里写了 `2=输入/IO/参数错误`，只是有 4 条路径没走到。
  如果你的封装脚本把 `rc != 0` 一律当 fail 处理，**无需改动**；如果你写了 `if rc == 1: 判失败` 而把
  `rc == 2` 当"未知"放过，请改成 `rc != 0` 一律不放行。
- **MCP 通道**：`rc=2` 在封装层本来就映射为 **`isError: true`**（`lib/server.mjs` 的 `isExecFailure()`
  对 `status === 2` 返回 `true`，文案 `(执行层失败)`）。所以 MCP 调用方会看到的是**从"成功 + verdict=pass"
  变成"isError"**——这正是修复意图。请把"`isError` 为真"当作"**本次没有拿到核验结论**"，不要当作"核验没通过"。
- **不需要改的东西**：`mcp.json` 不用动、白名单不用重配、`.ioc` 不用动、`verify.json` 的字段结构不变。

## 已知限制

1. **仍不防 TOCTOU**：白名单校验通过后、真正打开文件前链接被替换，不在防御范围内。威胁模型是 agent 误操作，
   不是对抗者（与 0.7.0 一致）。
2. **参数级失明（本版未修，且短期修不了）**：7 项判据看的是"外设/引脚在不在"，**看不见 `.ioc` 里某个参数被改**。
   S4 预演实测：重新生成把 `PLLN 100→85`（SYSCLK 推算 200 → 170 MHz）悄悄改掉，**7 项一条都没报**。
   这类改动只能靠**生成前后 diff 逐条解释**，没有机器判据——接板前必须人工过一遍 diff。
3. **T6 在 CI 上恒为 SKIP**：`verify_generation` 那段没有进 CI 的机器判据（原因见上表）。要覆盖它只能跑
   `--require-materials`（需本机有真实素材），或将来引入一份**脱敏后入库**的完整素材集。
4. **日志特征层是"形态校验"，不是"语义校验"**：5 类特征 + 命中 ≥2 类只能把"随手一份文本"挡在门外，
   理论上"真实日志开头 + 伪造尾部"仍可穿过。它的目标是**提高造假成本**、消灭"忘了给参数所以永远 pass"
   这类**无意的**假绿，不是对抗**故意的**伪造——后者要靠 `docs/logs/` 的留存与人工对照。
5. **`regen.sh` 的缺参检测只覆盖"选项后无值"**：`--` 之后的位置参数、值本身以 `-` 开头、以及 `:276` 附近
   `set` 值比较的**精确小写边界**（`TRUE`/`True` 不命中）仍靠人工。另外脚本**没有文件锁**，两个 `regen.sh`
   并发跑同一工程会 lost-update（P2 未修，理由见 `docs/README.md` §2.1）。
6. **D 编号基准与"最新 tag"是两个独立判据**：`ci.yml` 只保证 `docs/README.md` 声明的 D 上限与
   `DECISIONS.md` 的实际最大号一致，**不保证正文引用的每个 D 编号都存在**。写错编号仍要人核。
