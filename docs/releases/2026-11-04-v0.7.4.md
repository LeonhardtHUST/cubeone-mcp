## ① 包体积双口径：0.7.3 正文的 `138.1 kB` 与台账的 `137.6 kB` 不矛盾

**事实**：`docs/releases/2026-11-04-v0.7.3.md` 的验证等级表写的是 `npm pack --dry-run` → **20 files / 138.1 kB**，
而 `docs/releases/README.md` §2、看板与本仓库 registry 上那个 tarball 是 **137.6 kB**。两个数字都对，量的是两份不同的包：

| 口径 | 怎么产生 | 0.7.3 实测 |
|---|---|---|
| **本机 CRLF pack** | 在 Windows 工作区跑 `npm pack`，把**工作区行尾**打进 tarball | `138.1 kB` |
| **CI LF pack** | 在 CI 的干净 LF checkout 里打包（= 真正发布到 registry 的那个） | `137.6 kB` |

**根因**：`.gitattributes` 要求 index 存 LF（`*.py` / `*.md` 为 `text eol=lf`），但**工作区文件可以是 CRLF**。
`git status` 按**归一化后**比较，所以显示"干净"——**这让差异完全隐形**。每多一个 CRLF 文件，本机 pack 就多几十字节。

**两者内容一致**：去掉 CR 之后，包内文件与 registry tarball **逐字节相等**，差异只有行尾字节与由此产生的体积差。

**不追改已发布的 0.7.3 正文**：改它会破坏「GitHub Release 正文与 `docs/releases/*.md` 逐字一致」这条证据
（D35 §35.6 人工核第 2 项）。所以该口径只在本版正文与 `docs/releases/README.md` 的台账脚注里澄清。

> 本版起，**包体积不再用本机数字冒充 CI 数字**——见下一节。

## ② CRLF 归一处置：发版证据只认 CI 的 LF pack（硬纪律）

**规则（自 0.7.4 起，必须）**：**包内容证据（files 数 / 体积 / tarball 清单）一律取自 CI 的 LF checkout**。
本机 `npm pack` 的尺寸**只能作参考，不得写进发版正文或台账作为包体积证据**——唯一例外是先确认
`git ls-files --eol | grep -c 'w/crlf'` 为 **0**。

**这一条为什么是"纪律"而不是"修一下"**：把工作区强制重检出为 LF 确实能让计数归零，但它是**环境操作、不持久**
（CubeMX 或编辑器保存后可再现），而且因为 `git status` 本来就显示干净，**很容易误判成"已根治"**。
把证据锚到 CI 的干净 checkout，才可复现、可审计、与 §35.6 人工核第 3 项一致。

**陷阱一句话**：**`git status` 干净 ≠ 工作区逐字节等于 index**。
**本版实测**：发版时 `git ls-files --eol | grep -c 'w/crlf'` = **20**（P2 落盘时是 21；差别来自这几页文档被重写后的落盘行尾）。
**如实记录、不声称清零**——清零不是硬要求，硬纪律是"发版走 CI"。自检命令（可选，不产生 commit）见
`docs/README.md` §2.1 第 5 条。

## ③ `KO` 正则复测提示：大小写敏感，CubeMX 改版时要复测

`regen.sh` 与 `verify_generation.py` 判"生成阶段失败"用的是**整行 `KO`**（CubeMX 退出码恒为 0，见 D25）：

```
^[[:space:]]*KO[[:space:]]*$     ← regen.sh 的 grep（大写）
^\s*KO\s*$                       ← verify_generation.py 的 _KO_LINE_RE（大写）
```

**它大小写敏感**：`ko` / `Ko` **不命中**。若 CubeMX 改版后输出形态变化（大小写、行首缩进、计数前缀、行尾空白
任一变了），**必须复测此正则并补一条真实日志的负样本**——否则"整行 KO"会静默漏检，而漏检的表现恰好是**假绿**。
**本版只补提示、不改正则本体**：改正则属判据变更，得先有真实形态证据。提示已写进
`references/regen-exit-codes.md` §3。

## ④ `tools/*` 编码加固：门禁脚本不再因控制台编码崩溃

`scripts/` 三个脚本的编码加固是 0.7.2 做的（`tests/test_console_encoding.py`，10 例），但**门禁脚本 `tools/*` 一直没被覆盖**
——它们恰恰是**发版前必跑的四条命令**之一，却只在"本机代码页恰好是 UTF-8"的环境里被执行过（审定报告 §4.7 / **B-5**）。

- **读**：`tools/check_release.py` / `tools/check_taskboard.py` 读文档一律 `errors="replace"`。
  坏字节由替换字符顶替，**判据照样出结论**；读不出来时**判红并点名**，不抛 `UnicodeDecodeError` 把整道门禁打崩。
- **子进程**：`git` / `npm` 调用显式 `encoding="utf-8", errors="replace"`。
- **写**：按输出目标分流（与 `scripts/` 同款）——**管道/重定向强制 UTF-8**（CI 日志与 `$(...)` 消费，UTF-8 唯一无歧义）；
  **交互式控制台保留自身编码**（中文 Windows = cp936 中文正常），只把 errors 换成 `backslashreplace`
  （英文 Windows 的 cp1252 打印 `✓` / `✗` / 中文不再抛 `UnicodeEncodeError`）。
- **`tools/npm_mcp_handshake.mjs`**：落盘本来就是 UTF-8（Node 对 stdout 也一律写 UTF-8 字节、不按控制台代码页转码），
  所以它的失败模式不是"编码崩"而是**管道被下游提前关闭**（`node … | head -5`）时的 `EPIPE` 未捕获异常
  ⇒ 冒烟以"崩溃"结束而不是给 PASS/FAIL。已加 EPIPE 守卫（**判据与退出码逻辑零改动**）。

回归：`tests/test_tools_encoding.py`（9 例），含**反证**——把分流函数换成 `pass` 后，cp1252 管道下
`UnicodeEncodeError` + rc=1（所以这套用例不是"恒绿摆设"）。
⚠️ 其中**Node 那 1 例在 CI 上显式 SKIP**：CI 的 pytest job 不跑 `npm ci`，而 `npm_mcp_handshake.mjs` 开头是
静态 `import @modelcontextprotocol/sdk`（ESM 的 import 在模块体**之前**求值）⇒ 没装依赖时进程以
`ERR_MODULE_NOT_FOUND` 退 1，连参数校验都到不了。这是"**验证对象在 CI 上不可达**"（本仓惯例：显式 SKIP 并说明原因），
不是"测过了"。

## ⑤ 版本轴：从「四处」扩到「五处」，且五处机器可验

`tools/check_release.py` 的判据① 现在比 **五处**（此前四处）：

| # | 位置 | 谁在消费 |
|---|---|---|
| 1 | `package.json` → `version` | npm 包版本 / `npm publish` 的版本来源 |
| 2 | `package-lock.json` → 根 `version` | `npm ci` 的锁根 |
| 3 | `package-lock.json` → `packages[""].version` | lockfileVersion 2/3 的包根记录 |
| 4 | `SKILL.md` → frontmatter `version` | Agent 操作面的文档迭代号 |
| 5 | `README.md` → 「三个版本号」表两处 | 人读的对外快照 |
| — | `git tag` `vX.Y.Z` | 发布锚点（与五处比对，但不算"五处"之一） |
| — | `verify_generation.py --version`（`1.2.0`） | 判据契约轴，**故意独立**（D33 §33.2），不并入 |

**为什么加 2/3**：`npm install` 会自动把 lock 根同步成 `package.json.version`，所以漂移只有一个来源——
**手改 `package.json.version` 却没跑 `npm install --package-lock-only`**。这种漂移在旧的四处口径下**完全看不见**
（四处都已是新版本，只有 lock 停在旧值），而 `npm ci` 与发布产物**都以 lock 为准**；等暴露时通常已经是 CI 红
或 registry 上出现旧版本。「五处」如果只是句口号、没有机器比对，就等于把规则又交回人手。

**判据① 的预期 FAIL 形态**（与旧口径同义，只是明细多两行）：

```
[FAIL] 判据① 版本轴同值 — 最新 tag=0.7.3，但 package-lock.json 根=0.7.4；package-lock.json packages[""]=0.7.4
```

**打 tag 之前看到这条红是预期的**——它证明的正是"版本号改了、tag 还没打"这个真实状态（D35 §35.2）。
打 tag 之后转 PASS。决策与理由见 **D35 §35.7**（在 D35 内追加，**不新增 D37**；§35.2 step0 原文不改，按"更正只追加"约定）。

## 已知限制

1. **仍不防 TOCTOU**：白名单校验通过后、真正打开文件前链接被替换，不在防御范围内。威胁模型是 agent 误操作，
   不是对抗者（与 0.7.0 一致）。
2. **参数级失明（本版未修，且短期修不了）**：7 项判据看的是"外设/引脚在不在"，**看不见 `.ioc` 里某个参数被改**。
   S4 预演实测：重新生成把 `PLLN 100→85`（SYSCLK 推算 200 → 170 MHz）悄悄改掉，**7 项一条都没报**。
   这类改动只能靠**生成前后 diff 逐条解释**，没有机器判据——接板前必须人工过一遍 diff。
3. **T6 在 CI 上恒为 SKIP**：`verify_generation` 那段没有进 CI 的机器判据（缺真实素材）。要覆盖它只能跑
   `--require-materials`（需本机有真实素材），或将来引入一份**脱敏后入库**的完整素材集。
4. **日志特征层是"形态校验"，不是"语义校验"**：5 类特征 + 命中 ≥2 类只能把"随手一份文本"挡在门外，
   理论上"真实日志开头 + 伪造尾部"仍可穿过。目标是**提高造假成本**、消灭"忘了给参数所以永远 pass"这类
   **无意的**假绿，不是对抗**故意的**伪造。
5. **`regen.sh` 的缺参检测只覆盖"选项后无值"**：`--` 之后的位置参数、值本身以 `-` 开头、以及 `:276` 附近
   `set` 值比较的**精确小写边界**（`TRUE` / `True` 不命中）仍靠人工。同样地，`regen.sh` **没有文件锁**，
   两个实例并发跑同一工程会 lost-update——**这一条本版仍未修**（跨步骤文件锁排在 **0.8.0**）。
6. **双会话 lost-update 仍无锁（本版只登记、不改实现）**：同一工程目录并发执行两个会话时，
   `ioc-backup.json` / `*.ioc.bak` / `.ioc` 可能互相覆盖；`ioc_backup.py` 的 SHA-256 完整性校验能**检测**
   部分覆盖但不能**阻止**。规避：遵守单写者原则。真正的锁在 **0.8.0**（`ioc_backup` / `ioc_field` 同批）。
7. **本机工作区仍有 CRLF（`w/crlf` = 20）且不打算清零**：清零是环境操作、不持久，且 `git status` 看不出差异，
   容易误判"已根治"。**硬纪律是发版证据只认 CI 的 LF pack**（见 ②），不是"把本机弄干净"。
8. **`tools/check_release.py` 仍不挂 CI**：本仓的正常状态是"长期存在未发版改动"，那种状态下判据①本来就会红；
   挂进 CI 会让每次 push 都红、红灯失去信息量。正确用法是**发布前手动跑**（GATE-3.1 证据包的一项）。
