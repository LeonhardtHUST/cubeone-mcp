## ① 0.8.0 的 Release 正文行尾修正（唯一动过已发布证据的一处，用户明确授权）

**症状**：0.8.0 的 GitHub Release body 是 **13916 B / 182 个 CR**，而 `git show v0.8.0:docs/releases/2026-11-05-v0.8.0.md`
的 blob 是 **13734 B / CR=0**。**去掉 CR 后内容逐字节相等**——差的就是 182 个回车。

**根因**：`gh release create --notes-file <工作区文件>` 读的是**工作区**那份 `.md`，而工作区该文件是 CRLF
（`.gitattributes` 只强制 index 存 LF，工作区行尾不受约束）。

**处置**（合规路径，不是"回改正文"）：用 `git show v0.8.0:docs/releases/2026-11-05-v0.8.0.md` 导出 **LF** 内容，
`gh release edit v0.8.0 --notes-file <LF 临时文件>` 重发 body。**入库文件本来就没有 CR，一个字节都没动**；`tag` 未动；
npm 包未动；**正文文字零改动**。

**核验（字节模式，不用文本模式——Windows 文本模式会自动 CRLF↔LF，会把这事看糊）**：

| 对象 | 字节 | CR | 与 v0.8.0 blob 逐字节相等 |
|---|---|---|---|
| 修正前 body | 13916 | **182** | ❌（去 CR 后相等） |
| 修正后 body | **13734** | **0** | ✅ |
| `git show v0.8.0:` 的 blob | 13734 | 0 | （基准） |

字节差 **−182**，内容零变化。**这是本版最重要的一条验收**：0.7.3 / 0.7.4 / 0.8.0 / 0.8.1 四份正文现在**都是** CR=0、
与各自 blob 逐字节相等。

> 纪律已固化在 `docs/releases/README.md`「发版证据口径」：`--notes-file` **必须**指向 `git show HEAD:<path>` 导出的
> LF 内容；D35 §35.6 人工核第 2 项的判据是「与 **HEAD blob** 逐字节一致」，不是「与工作区文件一致」。
> 本版（0.8.1）的 Release 正文就是按这条纪律发的。

## ② 陈旧锁回收后**立即重试**：消除 `--lock-timeout 0` 的自相矛盾

**症状**：锁文件已陈旧（mtime 超 300s）时用 `--lock-timeout 0`，第一次仍然 **rc=2**，还会打印
「（另一进程正在改同一工程？用 --lock-timeout 调大等待）」——可我们刚刚判定并**回收**了那把锁，等于自己打自己脸。

**根因**：`except FileExistsError` 里先 `_reclaim_stale_lock()`，紧接着就判 `deadline`。`timeout=0` 的 deadline 在
循环开始时就到了，于是"刚把死锁收掉"立刻按超时失败。

**修法**：`_reclaim_stale_lock()` 改为返回 `bool`；**回收成功就无条件 `continue` 再试一次**，不看 deadline；
只有**没回收**才走 deadline 判断。两个脚本各持一份实现，**都改了**。

| 场景 | 0.8.0 | 0.8.1 |
|---|---|---|
| 陈旧锁 + `--lock-timeout 0` | rc=2，要跑第二次才成功，且文案误导 | **第一次就 rc=0 且写入生效** |
| **新鲜**锁 + `--lock-timeout 0` | rc=2 | **仍 rc=2**（活锁必须挡住——这条修正不得变成"无脑重试"） |
| 陈旧锁 + 默认超时 | 回收后继续（行为不变） | 回收后立即重试（少一次 0.1s 轮询） |

## ③ `outputSchema` 的 `_meta` 声明：三工具对齐五字段

**症状**：`verify_generation` 的 `outputSchema.properties._meta` 展开了五个字段，而 `ioc_backup` / `ioc_field`
只写 `{ "type": "object" }`——同一份契约三种写法。

**影响**：**不影响任何客户端**（`_meta` 是可选字段，三处都**没有** `additionalProperties: false`，校验行为等价）。
真正的问题是**维护性**：下次改 `_meta` 很容易只改一处。

**修法**：两处细化为与 `verify_generation` 一致的五字段（`truncated` / `original_bytes` / `limit_bytes` / `policy` /
`truncated_fields`），**仍然可选**（不在 `required`）、**仍然不封闭**（不加 `additionalProperties: false`）。
新增节点测试把三者字段集合绑在一起。

## ④ 正文纪律落地（无代码）

`docs/releases/README.md`「发版证据口径」补两条硬纪律，并自本版起执行：

1. **正文不写 `w/crlf` 的具体数字**（含区间）：它随文档写盘实时变动，给了数字读者就会当判据、然后必然对不上。
   正文只写「`w/crlf` > 0 时本机 pack 一律不作证据，证据只认 CI 的 LF pack」。要留痕就记进**台账脚注**（带日期）。
2. **验证表的 CI 行必须指「发版 commit」那条 run**，不是修复 commit / 回填 commit 的 run——发版证据要回答的是
   "**发版那个 commit 本身绿不绿**"。
