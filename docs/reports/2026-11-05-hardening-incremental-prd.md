## 1. 目标（各一句话，可度量）

### 1.1 W0-4 目标

把「任意拼接 ≥2 类特征词即可冒充生成日志」的攻击面，收窄为「必须复现 CubeMX 日志的**结构性骨架**（时间戳 + 级别 + logger/log4j 结构化字段）」——使**已知伪造样本 100% 被拒、真实回归日志 0 误伤**；不承诺对抗逐字节蓄意伪造（那需来源校验/签名，见 §4）。

- 度量：已知 5 类伪造负样本拒绝率 **100%**；7 份真实日志形态层放行率 **100%**（素材齐全时）；对真实日志的**假阳性允许值 = 0**。

### 1.2 W0-2 目标

把「`--project-root` 下 `Core/Src/*.c` 非空」的存在性代理，升级为「`main.c` 含可识别的 CubeMX 生成骨架（`int main` / `MX_*_Init` / `SystemClock_Config` 等至少 N 项结构性符号）」——使「空壳/假工程」目录被拒、真实工程 0 误伤。

- 度量：假工程（有 `.c` 但无生成骨架）拒绝率 **100%**；真实工程目录形态层放行率 **100%**；对真实工程的**假阳性允许值 = 0**。

## 2. 用户故事（三类用户 × 两个缺口）

**用户 ①：被 agent 自动化调用的维护者**（Agent 通过 MCP 通道编排核验）
- 作为**把 `verify_generation` 接进 Agent 自动流程的维护者**，我需要「伪造/空壳输入被拒」而不是拿到一个 `verdict=PASS`，以便我收到的绿灯代表「真的生成过、真的在目标工程上」，而不是「有人随手拼了两行日志 / 指了个空壳目录」。
- 作为同一维护者，我需要加固后**真实日志仍然放行**，以便自动化流程不会因为核验器变严而对正常生成报假红、天天救火。

**用户 ②：手工跑 CLI 的工程师**
- 作为**在本地手工跑 `verify_generation.py` 的工程师**，我需要核验器能识破「我拿错了日志/指错了工程根」这类常见误操作并给出**可读的拒绝理由**，以便我立刻知道是日志不是日志、还是工程根选错，而不是拿着假 `PASS` 去烧板。
- 作为同一工程师，我需要拒绝理由**点名具体缺哪类结构**（如「日志缺少 log4j 结构化字段」/「main.c 未发现 MX_*_Init」），以便我能自己修，不用猜。

**用户 ③：把 `verify.json` 接进自己流水线的人**
- 作为**消费 `verify.json` 的下游流水线作者**，我需要加固后的退出码语义不变（证据不成立 = `rc=2`、无结论；生成失败 = `rc=1`、有结论 fail），以便我的 `if rc != 0 判失败` 逻辑无需改动、且能区分「没验成」与「验出问题」。
- 作为同一下游作者，我需要 7 项判据的 `checks` 数组**语义与长度不变**（恒 7），以便我的解析器不因加固而崩。

## 4. 不做清单（明确划界，防设计扩张）

1. **不做**「读 CubeMX 二进制签名 / 校验 exe 哈希」——跨平台不可移植，且日志可能来自别的机器。
2. **不做**「对日志内容做语义 NLP 判断」——不可复现、不可机器判据化。
3. **不动** 7 项判据、**不加**第 8 个 check、**不改** `schema /2`（F-1）。加固只在 `validate_evidence_inputs()` 前置层。
4. **不改** 已有 `--log` 的 CLI 参数名与退出码 `{0,1,2}` 语义（`0`=pass / `1`=有结论 fail / `2`=无结论）。
5. **不做**「日志来源强绑定」（如强制 `--log` 必须由 `regen.sh` 重定向产生、必须与工程根同目录）——**误伤风险高**（用户可用别的机器/重命名的日志），见 §5.2。
6. **不把**形态校验写成**严格模板**（固定行序 / 行数 / 前缀）——F-1 核心边界。

## 5. 候选方向价值比较（给架构师取舍用，不替其定方案）

> 只比较**价值与代价**，不下结论；每个方向须自证「不制造 F-1 新假红」。

| 方向 | 能挡住什么 | 挡不住什么 | 对真实日志误伤风险 | 与 F-1 关系 |
|---|---|---|---|---|
| **D1 特征加权**（log4j 结构化字段权重 > 标题行） | 只拼「标题行 + LoadConfig」的低成本伪造（如 N1，因结构化字段权重不足被拒） | 复刻了 log4j 骨架（`YYYY-MM-DD HH:MM:SS,mmm [INFO] logger:line - msg`）的伪造 | **低**（真实日志本就是 log4j 格式，t1.8 实测行结构含时间戳+`[INFO]`+logger） | 安全：加权不是固定模板；需确认多版本真实日志都含 log4j 字段 |
| **D2 类别深度**（要求 ≥1 类「结构性」特征，如 `End LoadConfig()` / `log4j2` / 时间戳+级别组合） | 拼接「标题/动作」类（C1+C2）的伪造（它们不算结构性） | 伪造者知道规则后补一条结构性特征（成本仍低） | **中低**（需确认真实日志都含 C4/C5 结构性类；v0.7.3 注释称正向样本命中 3~5 类） | 需谨慎：只能「增加结构要求」，**不得固定具体行/前缀**，否则滑向严格模板 |
| **D3 日志来源校验**（路径与工程根关系 / 是否 regen.sh 产物命名） | 手工拼凑的任意路径文件 | 把伪造文件放到「正确位置/正确命名」；跨机器日志 | **高**（工程根外日志、重命名、别的机器日志都会假红） | 与「日志可能来自别的机器」（不做清单 1）冲突，**慎用** |
| **D4 阈值提到 3 类** | 只拼 2 类（N1）的伪造 | 拼 3 类的伪造（成本仍低，治标） | **中低**（需确认 7 份真实日志都命中 ≥3 类；注释说 3~5 类，但需实测确认而非假设） | 安全但**治标**：提高门槛≠提高结构；不得只调数字就宣称加固 |
| **W0-2 内容指纹**（`main.c` 含 `int main` / `MX_*_Init` / `SystemClock_Config`） | 空目录、空 `.c`、非 STM32 工程、空壳工程（N6） | 「真实但选错到另一个真实工程」仍像工程 | **低**（真实 `main.c` 必然含这些符号），但需覆盖 CubeMX 布局差异（`CoupleFile=true/false` 时定义在 periph 文件） | 安全：符号存在性判据，非模板；需在给了 `--project-root` 时扫 `Core/Src/*.c` 全量 |

**组合提示（供架构师参考，非定案）**：D1（加权）+ D2（≥1 结构性类）在保住 F-1「不固定模板」前提下最能收窄低成本伪造；D4 可作兜底但不能单独宣称加固；W0-2 内容指纹独立于日志侧、误伤最低，可优先落地。D3 因误伤风险高，**默认不建议**（除非用户明确接受跨机器日志被拒）。
