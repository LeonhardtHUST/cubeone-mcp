## 5. 步骤 E：diff 取证（🔴 判据必须用 `git diff`，不能用 `git status`）

```bash
echo "--- git status（会虚高，仅供参考） ---"
git -C testbeds/template-mcu-STM32G474-series status --porcelain
echo "--- git diff --numstat（唯一权威判据） ---"
git -C testbeds/template-mcu-STM32G474-series diff --numstat
echo "--- 行尾证据 ---"
git -C testbeds/template-mcu-STM32G474-series ls-files --eol | head -20
```

**干跑实测的对照值（正式跑应当同构）**

```
git status --porcelain   →  8 个 M      ← 其中 6 个是 CRLF-only 假阳性
git diff --numstat       →  只有 2 个真改
   11  0  Core/Src/main.c
    9  6  stm32-g474-template.ioc
```

**原因**：CubeMX 把文件写成 CRLF（`w/crlf`），index 是 LF；`.gitattributes` 的 `* text=auto eol=lf` 只在 `diff`/`add` 时归一化，`status` 仍按字节判脏。

> **DoD「diff 仅含预期文件」必须按 `git diff --numstat` 判。** 按 `status` 判会把 6 个 CRLF-only 文件当成越界。

## 7. 失败处置（退出码三格语义，v1.1）

`regen.sh` 退出码语义已扩展（因为 **CubeMX 退出码恒为 0**，只看它等于没有判据；v1.1 改为"生成日志出现整行 `KO` ⇒ 判生成失败"）：

| 退出码 | 含义 | 我的处置 |
|---|---|---|
| **`0`** | 生成 + 核验通过 | 继续步骤 C（双判据）→ 步骤 D `pio run` |
| **`1`** | **跑过了但错了，已回滚** | **看 stderr 前缀区分**：`[regen] 生成阶段失败` = 被脚本层判据拒（含 `KO` 判据）；`[regen] 核验阶段失败` = 生成成功但产物不对。两种都要：先 `git checkout -- Core/`（回滚只覆盖 `.ioc`+`.mxproject`），再取证据 |
| **`2`** | **压根没跑**（工程不存在 / 找不到 java / `--require-clean` 命中脏 / 参数错） | **不要去看核验报告**，那是白费工夫。直接查 `s1-regen-console.log` 的前置检查段 |

| 失败点 | 处置 |
|---|---|
| 步骤 A 回显 `KO` | 停下。`.ioc` 未被修改（干跑已证实 KO 时内容不变）。把日志给 lead |
| A4 `Mcu.IPNb` 变 4 | **越界**，`git -C <testbed> checkout -- .` 回滚，报 lead |
| 步骤 B `rc=1` | 按上表区分阶段。回滚后**自己** `git checkout -- Core/` 再取证 |
| 步骤 B `rc=2` | 前置/参数/环境问题。查 `s1-regen-console.log` |
| `verify.json` 是 `/1` 的 5 项 | **跑的是旧脚本 → 证据无效**，报 lead 并重跑 |
| C-3 整行 `KO` > 0 | 与 `regen.sh` 的判据交叉确认；若 `regen.sh` 说 pass 而 KO>0，**这是脚本判据的漏洞，报 verifier-dev** |
| 步骤 D 告警 >0 | 该工程对自身源码开 `-Werror`，有告警即构建失败。记录并报 lead |
| after ≠ 3792/1584 | 不掩盖。**第一步先排除 `-e` 用错**（必须是 `-e GPIO`，不能是 `GPIO,PB0`）；再排除 `.pio` 污染（`rm -rf .pio` 重建一次再比） |
