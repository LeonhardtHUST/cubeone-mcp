### 6.2 ⚠️ 构建过程中踩到的一个环境问题（已在日志留痕）

**第 1 次尝试（12:23:30）卡死 5m50s 后被杀**。日志末尾出现：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn",
  "targets":["…\FrameworkHALDriver\Src\stm32g4xx_hal_sai.o"],"targetCount":1}
```

**根因**：CubeMX 生成把 `Core/Inc/stm32g4xx_hal_conf.h` 改写为 CRLF → mtime/内容变化 → SCons 判定 HAL 全部依赖失效 → 全量重编 → 删除第 50 个旧 `.o` 时触发**本机 safe-delete 拦截器的批量删除阈值**，进程挂起等人工确认，而无人可确认。

**对照证据**：11:59 基线构建、12:08 干跑构建（两者都是**空 `.pio` 全量构建、零删除**）日志中 `safe-delete` 出现次数均为 **0**。

**第 2 次尝试（成功）**：改用全新构建目录 `PLATFORMIO_BUILD_DIR=.pio/build-s1` → 零删除 → 不触发拦截 → 12.06 s 完成。

> **等价性说明**：源码、`platformio.ini`、`boards/` 全部未改，仅换 build 输出目录，属**从头全量构建**，对 L3 判定**等价或更强**（排除了增量构建的缓存干扰）。`platformio.ini` **未被修改**，P7 的 diff 面不受影响。
> **对团队的提示**：这是本机环境的通用障碍——**任何"改了 `Core/Inc/*.h` 后的增量重建"都会触发**。建议 SKILL.md 记录规避方式（换 build 目录或先清空 `.pio`）。**注意这不是 PlatformIO/CubeMX 的缺陷。**
