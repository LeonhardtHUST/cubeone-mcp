## 1. 🔴 核心发现：纯透传通道**只能配普通 GPIO，配不了任何外设**

### 1.1 三个探测及其结果

在丢弃副本 `testbeds/_s3-probe/g474`（从 G474 基线克隆）上，用 CLI 等价通道（= `cubemx_configure` 的逐字实现）依次试了三种语法：

| # | 命令 | 回显 | `.ioc` 实际变化 | CubeMX 退出码 |
|---|---|---|---|---|
| 1 | `set pin PA0 S_TIM2_CH1_ETR` | **`KO`** | 无（`IPNb=3`、`PinsNb=5` 未变） | **0** |
| 2 | `set pin PA0-WKUP S_TIM2_CH1_ETR` | **`KO`** | 无 | **0** |
| 3 | `set ip parameters TIM2 InputCapture PA0-WKUP S_TIM2_CH1_ETR Prescaler 65535` | **`OK`** ⚠️ | **无！**（`.ioc` 里连 `TIM2` 字样都没出现） | **0** |
| 4 | `set pin PA1 USART2_TX` | **`KO`** | 无 | **0** |

原始回显（`s3-probe2-raw.log` 587–601 行，逐字）：

```
config load "D:/…/stm32-g474-template.ioc"
OK
set pin PA0-WKUP S_TIM2_CH1_ETR
KO
set ip parameters TIM2 InputCapture PA0-WKUP S_TIM2_CH1_ETR Prescaler 65535
OK
set pin PA1 USART2_TX
KO
config saveas "D:/…/stm32-g474-template.ioc"
OK
exit
Bye bye
```

### 1.2 三条结论

1. **`set pin <pin> <外设信号>` → `KO`**。带外设信号名（`S_TIM2_CH1_ETR` / `USART2_TX`）一律失败。唯一的成功形态是**普通引脚模式** `set pin PB0 GPIO_Output`（干跑已验 `OK`）。
2. **`set ip parameters <IP> ...` → `OK` 但是静默空操作**。这是**最危险**的形态：返回 OK、退出码 0、`.ioc` 一字未变。任何"看返回值判断成功"的逻辑都会被它骗过。根因与 env-agent 源码结论一致：TIM 伪命令（`_inject_tim_*`）**只被 `cubemx_new_project` 调用**，纯透传路径下这些命令被原样喂给 CubeMX 脚本解释器，解释器接受了语法但没有后端处理。
3. **CubeMX 进程退出码恒为 0**，即使有 `KO`。→ **退出码不能作为成功判据**；只有**回显行**（`OK`/`KO`）与**生成物**可信。

### 1.3 影响面（升级为产品级问题）

| 对象 | 影响 |
|---|---|
| `cubemx_configure` / `cubemx_script`（纯透传） | **只能做 GPIO 引脚配置**。加 UART/SPI/I2C/TIM/ADC **全部不可行** —— 要么 `KO`（可察觉），要么 `OK` 空操作（不可察觉） |
| `cubemx_new_project` | 是唯一能建外设的路径，但 **G474 用不了**（本机只有 `STM32F103C8T6.ioc` 模板，env-agent 已实读源码确认） |
| **SKILL.md** | **必须写明这条能力边界**。否则使用者会以为"用 `cubemx_configure` 就能加串口"，得到 `OK` 然后以为成功 —— 比报错更糟 |
| **S3(a) 原计划** | **第一步走不通**，见下节 |

## 2. S3(a) 原计划不成立，改用**文本编辑 `.ioc`** 路线

### 2.1 verifier-dev 原建议（需废弃）

> 1. 先建基线：用 CLI `set` 在 PA0 上配 TIM2_CH1（正确写法 `S_TIM2_CH1_ETR`，D4）→ `regen.sh -e GPIO,TIM2` 应 PASS

**这条第 1 步实测不可行**：`set pin PA0-WKUP S_TIM2_CH1_ETR` → `KO`；`set ip parameters ...` → `OK` 但没建出 TIM2。所以**无法用纯透传造出 TIM2 基线**。

### 2.2 修正方案：文本编辑 `.ioc`（这正是 D3–D5 警示的那条路，也正好被 S3 验到）

这条路本身就是模板 `AGENTS.md` §2.3 与 `TEMPLATE-PLACEHOLDERS.md` D3–D5 描述的"手改 `.ioc` 必须同步白名单"场景，用它做 S3 反而**更贴题**。

#### 需要的键形态（来自真实 G474 `.ioc`，只读取自 `NUEDC_2027/G474/G474_05_adc_periodic_irq/Project.ioc`）

```
Mcu.IP6=TIM6
Mcu.IP7=TIM17
Mcu.IPNb=9
TIM17.IPParameters=Prescaler,PeriodNoDither
TIM17.PeriodNoDither=9999
TIM17.Prescaler=199
VP_TIM17_VS_ClockSourceINT.Mode=Enable_Timer
VP_TIM17_VS_ClockSourceINT.Signal=VP_TIM17_VS_ClockSourceINT
```

**关键观察**：一个"内部时钟"的定时器在 `.ioc` 里需要**四类东西同时到位**：
1. `Mcu.IP*` 里加该 IP 名 + `Mcu.IPNb` 递增
2. `<IP>.IPParameters` **白名单**
3. 白名单里列出的**每个参数值**
4. **`VP_<IP>_VS_ClockSourceINT` 虚拟引脚**（`Mcu.Pin*` + `Mcu.PinsNb` 也要同步加）

少任何一类都可能触发"静默丢弃"——这正是 H-6（TIM4 消失）的成因。

#### S3(a) 执行序列（**两步，判据不同**）

| 步 | 操作 | 期望 |
|---|---|---|
| **a-0** | 在 G474 testbed `.ioc` 里文本加入 **完整正确** 的 TIM2（内部时钟 + 1 通道输出或输入捕获），四类键齐备 | — |
| **a-1** | `regen.sh -e GPIO,TIM2` | **PASS**，`main.c` 出现 `MX_TIM2_Init` 定义 + 调用 → **这就是对照组**，同时证明"加外设能过" |
| **a-2** | 把 `PA0.Signal=S_TIM2_CH1_ETR` 改成 `PA0.Signal=TIM2_CH1`（**去掉 `S_` 前缀**，D4 陷阱） | — |
| **a-3** | `regen.sh -e GPIO,TIM2` | **rc=1**；`log_cannot_map` **fail（真实日志）** + `main_init_present` fail；自动回滚 |

**a-3 是整个 G1 最关键的证据**：它产出的 `cubemx-generate.log` 里将出现**真实的** `Cannot map signal` 行 —— 这一行是核验器 `log_cannot_map` 的**唯一真实输入样本**，此前所有人的验证都只有合成日志或 fixture。

### 2.3 S3(b)：TIM4 漏 `IPParameters`（判据与 (a) 不同，不可合并）

> **🔼 lead 已定执行顺序：先 (b)，后 (a)。** 理由：(b) 的日志**完全干净**，只有查 `main.c` 才能发现外设没了 —— 这才是"**没有核验器 = 看不见**"的证明，是项目说服使用者"为什么必须跑 G1"的主证据。(a) 失败时日志已能抓住，任何 `grep "Cannot map"` 的土办法都够用，故降为第二步（其独立价值 = 全队第一个真实 `Cannot map` 样本，供校准正则）。
> **若时间不足，只交 (b) 也算 S3 达标**，但报告必须显式写明"只完成 (b)"。

| 步 | 操作 | 期望 |
|---|---|---|
| b-0 | `.ioc` 里加 `Mcu.IP*=TIM4` + `VP_TIM4_VS_ClockSourceINT`，但**故意不写** `TIM4.IPParameters`（或不写白名单里列出的参数值） | — |
| b-1 | `regen.sh -e GPIO,TIM4` | **rc=1**；**`log_cannot_map` 仍 `pass`**（干净日志！）+ `main_init_present` **fail**（`TIM4(missing)`） |

**两个负样本的判据差异**（verifier-dev 特别强调，我认同）：

| | `log_cannot_map` | `main_init_present` | 说明什么 |
|---|---|---|---|
| **(a) 去 `S_` 前缀** | **fail** | fail | 信号映射阶段就被拒 → 有日志证据 |
| **(b) 漏白名单** | **pass** | fail | CubeMX 静默丢弃 → **日志干净**，只有生成物能发现 |

→ **(b) 才是"核验器不可替代"的真正证明**：日志说没问题，只有核验 `main.c` 才能发现外设没了。这正是调研报告 C2 / Gap-G1 的核心论点。

## 3. 日志通道记录要求（lead 明确要求，S3 必写）

`env-agent` 发现 `vscode-cube-mcp` 内部有 `NOISE_RE` 会**整行删除**形如 `YYYY-MM-DD HH:MM:SS,mmm [WARN]` 的日志行。**若 `Cannot map signal` 是这种形态，从 MCP 返回值里永远找不到 → 核验器若误读 MCP 返回值就会假阴性。**

→ **S3 的证据必须显式记录"日志从哪个通道取得"**：

| 通道 | 是否可信 | 本轮怎么用 |
|---|---|---|
| **原始 stdout 重定向落盘**（`java … -q … > log 2>&1`） | ✅ 最可信，未经过滤 | **本次 S1/S3 全走这个**（`regen.sh` 也是这么做的） |
| `regen.sh` 的 `-o` 落盘日志 | ✅ 同上（它就是 stdout 重定向） | 用 |
| MCP 工具返回值 | ❓ 经 `NOISE_RE` 过滤，可能**丢失 `[WARN]` 行** | **本次会话 MCP 未加载，无法验证**；须在 MCP 可用后单独验一次 |

**S3 报告必须写明**：`log_cannot_map` 的判定输入来自 **stdout 重定向落盘日志**，非 MCP 返回值。若将来切到 MCP 返回值通道，须先验证 `Cannot map` 行不被 `NOISE_RE` 吞掉。

**S3 附带产出**：把真实 `Cannot map` 行的**完整原文**贴进报告，供 verifier-dev 校准正则（他的 `_CANNOT_MAP_RE` 目前只见过 fixture 与合成样本）。

## 4. 对 S1 的一个附带修正

`set pin PB0 GPIO_Output` 是**普通引脚模式**（不是外设信号），所以 S1 路径**不受本发现影响**，干跑已实测 `OK` 并成功生成了 `GPIO_InitStruct`。**S1 方案不变。**

但 S1 报告里应加一句边界声明：

> 本场景只验证了**普通 GPIO 引脚**的配置路径。`cubemx_configure` 的纯透传通道**不支持外设信号**（`set pin <pin> <IP_SIGNAL>` → `KO`；`set ip parameters` → `OK` 但静默空操作），外设配置必须走 `cubemx_new_project`（G474 不可用）或文本编辑 `.ioc`。

## 5. 给 lead / verifier-dev 的三条结论

| # | 结论 | 严重度 |
|---|---|---|
| 1 | **`cubemx_configure` 只能配普通 GPIO**，配不了外设。且 `set ip parameters` 是**静默空操作（OK 但无效）** —— 已升为 `DECISIONS.md` **D25**：本工具链**不代做**非 GPIO 外设；G1 是非 GPIO 路径上**唯一的安全网** | 🔴 **最高**（D25） |

| 3 | **S3(a) 第一步需改道**：不能用 `set` 造 TIM2 基线，改用**文本编辑 `.ioc`**（附四类键的完整形态 + NUEDC 参考来源） | 🟡 中（改道即可，不阻塞） |
