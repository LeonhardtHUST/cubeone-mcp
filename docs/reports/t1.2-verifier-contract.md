## 0. 一句话

CubeMX 的"生成成功"根本不是成功判据：**它的退出码恒为 0**（脚本层回 `KO` 也返回 0，D25），
信号名写错只在日志留一行 `Cannot map` 而外设被静默丢弃（D5/H-6）。
所以本交付物的判据是两条：**日志里没有整行 `KO`** + **核验器 `verdict=pass`**。
`regen.sh` 把"备份 → 前置检查 → 生成 → 核验 → 失败回滚"串成一条命令，任何一步不过都从**备份**恢复，不把未核验的配置留在工作区。

## 1. `scripts/verify_generation.py`（v1.1.0）

### 1.1 CLI（参数名是契约，勿改）

```
python scripts/verify_generation.py \
    --log <cubeMX生成日志路径> \
    --main-c <工程/Core/Src/main.c> \
    --mxproject <工程/.mxproject> \
    --expect <外设名逗号分隔, 如 GPIO,TIM4,USART2> \
    [--ioc <工程/xxx.ioc>] \
    [--expect-pins PB0=GPIO_Output] \
    [--project-root <工程根>] \
    [--allow-signal VP_RIF_VS_RIF1] \
    [--json-out <输出路径>] \
    [--report-md <输出路径>]
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--log` | ✅ | CubeMX 生成日志。**必须是 CubeMX 进程的原始 stdout/stderr**（`regen.sh` 把 `-q` 全量重定向进来），不能是 MCP 工具返回的过滤后文本（见 §6.1） |
| `--main-c` | ✅ | 生成的 `Core/Src/main.c`（**唯一**能证明外设是否真的被生成的文件） |
| `--mxproject` | ✅ | 生成的 `.mxproject`（查盘符绝对路径） |
| `--expect` | ✅ | 期望外设清单；逗号/分号/空白分隔，大小写不敏感，自动去重转大写；传空串 `""` = 不检查外设（外设类检查 `skip`） |
| `--ioc` | ❌ | `.ioc` 路径，引脚级检查读 `<PIN>.Signal` 用；不传 → `pins_present` `skip` |
| `--expect-pins` | ❌ | 期望引脚，形式 `PIN=SIGNAL`（如 `PB0=GPIO_Output`），**可重复、可逗号分隔**；不传 → `pins_present` `skip` |
| `--project-root` | ❌ | 工程根目录：递归扫描其下 `*.mx` 并核验绝对路径**指向哪里**；不传 → 该项 `skip` |
| `--allow-signal` | ❌ | `Cannot map` 白名单，**可重复、可逗号分隔**。命中白名单的行降级为 `warn` |
| `--json-out` | ❌ | 结构化 JSON 报告（自动建父目录） |
| `--report-md` | ❌ | Markdown 报告（含表格，适合直接贴进证据文档） |
| `--version` | ❌ | 打印 `verify_generation.py 1.2.0 (schema platform32.verify_generation/2)` |

- `--ioc` **只服务引脚级检查**（v1.2 新增）：`AskForMigrate` / 版本戳仍由 `regen.sh` 的前置检查承担（见 §3.3），核验器不读 `.ioc` 的其它字段。
- **白名单默认值是空**（核验器必须纯净）。D8 的 `VP_RIF_VS_RIF1` 是**项目级**已知噪音，由 `regen.sh` 预置（`--no-default-allow` 可关）。两个入口默认值不同，所以**生效值必须落盘**到 `inputs.effective_allow_signals`，`regen.sh` 同时打到 console。
- `--expect-pins`（引脚级检查）在 **v1.2 实现**，语义见 §1.4 的 `pins_present`。

### 1.2 退出码

| 码 | 含义 | 下游动作 |
|---|---|---|
| `0` | 全部通过（**允许** `warn`，如 D8/D9/A1 占位符） | 可继续 `pio run` |
| `1` | 存在 `fail` 级问题（静默丢弃 / 路径指错地方） | **禁止**继续，回滚或修 `.ioc` |
| `2` | 输入/IO/参数错误（文件不存在、`--project-root` 不存在、报告写不了） | 修命令，**不代表配置有问题** |

字段约束（下游可依赖）：

- **顶层只有 4 个契约键 + 2 个 deprecated 兼容键**：`schema` / `verdict` / `checks` / `summary` / `inputs`，外加 `expect` / `allow_signals`（v1.1 兼容让步，**v1.2 删除**；`summary.notes` 里有 `deprecated` 提示）。**所有请求参数一律收在 `inputs` 下。**
- `checks` **恒为 7 条**，顺序固定：`log_cannot_map` → `main_init_present` → `main_init_called` → **`pins_present`** → `mxproject_abs_path` → `mx_script_abs_path` → `syscalls_path`；id 不得改名。
- `status ∈ {pass, warn, fail, skip}`。
- **`blocking: bool`** — 该检查**失败时**是否阻塞交付。它描述"检查的性质"，**不随本次 `status` 变化**：6 项里只有 `syscalls_path` 是 `false`；`pass` / `skip` 的检查仍为 `true`。
  （v1.0 曾用 `level: "error"|"warning"` 并由 `status` 派生 → 全 pass 的报告 6 项都显示 `error`，极易被误读成"有错"。该字段**已删除**。）
- `verdict = "fail"` 当且仅当 `summary.errors > 0`；`warn` / `skip` 不影响 verdict。
- `summary.notes` = 所有 `skip` 的原因 + `deprecated` 迁移提示（人能看懂"为什么某项没查"）。
- `inputs.tool` **保持对象**（`{"name","version"}`），便于扩展；不要用字符串。
- `inputs` 内路径是**绝对路径**；`project_root` 未提供时为 `null`；`effective_allow_signals` 是**生效**白名单（对账"同一份日志两个入口两种结论"的凭据）。
- `inputs.expect_pins` 是规范化后的 `["PB0=GPIO_Output", …]`；`inputs.ioc` 为 `.ioc` 绝对路径（未传则 `null`）。
- JSON **不含时间戳**（便于 diff 与快照比对）；时间戳只出现在 Markdown 报告里。

### 1.4 六个 check id 的判定逻辑

#### `log_cannot_map`（blocking）— 外设被静默丢弃的根因证据（D5 / H-6）

- 逐行匹配 `cannot\s+map`（大小写不敏感），记行号与原文（并抽出被丢弃的信号名）。
- 命中行若包含任一 `--allow-signal` 值（子串、大小写不敏感）→ 该行降级；全部命中行都被降级 → `warn`，否则 `fail`。
- 日志为**空/纯空白** → `warn`（"没错误"不能靠空日志证明）。
- `OptionalMessage_ERROR` 行**不参与判定**，只在 detail 报数量：G474 最小工程必有一条 `VP_RIF_VS_RIF1` 噪音（D8），判它等于永远报错。

#### `main_init_present`（blocking）— 期望外设是否真的有初始化函数**定义**

- 先对 `main.c` 做**注释/字符串剥离**（保留换行、行号不变）再解析，避免把注释里的"死定义"当成定义。
- 定义为 `MX_<...>_Init(...)` 后跟 `{`；跟 `;` 的是原型声明。
- 外设 → 符号**容错匹配**（顺序即优先级，大小写不敏感）：精确 `MX_<PERIPH>_Init` → 功能后缀 `MX_<PERIPH>_<FUNC>_Init`（`UART/USART/TIM/SPI/I2C/ADC/DAC/CAN/Device/Host/…`，如 `USART2` → `MX_USART2_UART_Init`）→ 唯一 `fuzzy`。
- **不做子树误匹配**：`--expect TIM` 不会匹配 `MX_TIM4_Init`（否则"少配一个定时器"会漏报）。
- detail 写出实际符号名 + 匹配方式 + 定义行号。

#### `main_init_called`（blocking）— 初始化函数是否在 `main()` 体内**被调用**

- 大括号配平定位 `int main(void) { … }`；找不到 `main` → `fail`。
- 体内搜 `\b<symbol>\s*\(`；注释已剥离，`/* MX_TIM4_Init(); */` **不算调用**。
- 只核验"确实有定义"的符号；一个定义都没有 → `skip`（不重复报同一根因）。

#### `pins_present`（blocking，**v1.2 新增**）— 引脚级增量是否真的生效

存在理由：`cubemx_configure` 可能回 `ok=True`（上游判据只有"退出码 0 且无整行 `KO`"）而 `.ioc` **实际没改**；生成成功、`MX_GPIO_Init` 本来就在（PC13 在用），于是外设级检查全 pass —— 用户以为改动生效了，其实什么都没发生。这是 D5/H-6 的**引脚级版本**，比整只外设被丢更常见。

判定（任一不满足 → `fail`）：

1. `.ioc` 里存在 `<PIN>.Signal`，且取值（大小写不敏感）与期望一致；
2. 该引脚所属端口的时钟使能出现在 `main.c`（`__HAL_RCC_GPIO<X>_CLK_ENABLE()`）—— 这一条才把"引脚真的进了生成物"变成可验证事实，而不只是"`.ioc` 里写了个键"。

- 参数 `--expect-pins PIN=SIGNAL`（可重复、可逗号分隔）；`--ioc` 提供 `.ioc`。任一缺失 → `skip`（向后兼容，零爆炸半径）。
- 引脚名 → 端口：`P<字母><数字>` → `GPIO<字母>`；非该形式（如 `VP_SYS_VS_Systick`）只做 `.ioc` 侧校验。
- detail 逐条列 `期望 X=Y，实际：未找到 / =Z` 或 `… + __HAL_RCC_GPIOB_CLK_ENABLE()`。
- **实测价值**（未改动的 G474 基线）：外设级 4 项全 pass，只有它报 fail —— 见 §4.1。

#### `mxproject_abs_path`（blocking）— 工程文件可移植性（TOOLING §3.2）

- 逐行匹配 `(?<![A-Za-z0-9])[A-Za-z]:[\\/]`；命中即 `fail`，报行号与截短内容。反向断言挡掉 `http://`、`file:///`。

#### `mx_script_abs_path`（blocking）— CubeMX 脚本的绝对路径**指向哪里**

**不是"有盘符就 fail"。** 依据模板 `TEMPLATE-PLACEHOLDERS.md` A1：**CubeMX 脚本不支持变量，`project path` 必须硬写绝对路径** —— "存在绝对路径"是**合规**的，缺陷是"指向别处"。

扫描 `<--project-root>/**/*.mx`（跳过 `.git`/`.pio`/`Drivers`/`Middlewares`/`node_modules`/`.venv`/`__pycache__`）。

| 命中内容 | status | 含义 |
|---|---|---|
| `__PROJECT_DIR__` 等 `__[A-Z_]+__` 占位符 | `warn` | 脚本未配置，直接跑会失败 |
| 归一化后 **== 工程根 / 在其内** | `pass` | 自指，A1 的正常形态 |
| 归一化后是工程根的**上级目录** | `warn` | 需配 `project name` 才落对目录，人工确认 |
| 归一化后**指向别处** | `fail` | 生成会写进另一个工程 |
| 无盘符路径 / 无 `.mx` / 未传 `--project-root` | `pass` / `skip` | 不适用 |

- 归一化：`/`→`\`、压缩重复分隔符、去尾分隔符、`casefold()`；**不做 `realpath`**（路径常指向另一台机器）。
- detail：`相对路径:行号: 片段（in_comment=true|false）`，截断 120 字符；**注释里的路径照样报**，只做标记。
- **这条检查回答的是**："这份脚本在当前这台机器、这个位置，还对不对"。`stm32-digital-clock` 的 `scripts/cubemx-init.mx` 写死 `D:\Projects\GitHub\HUSTRadio\stm32-digital-clock`：原机 `pass`，克隆到别处就是 `fail` —— 生成会写进另一个工程。

#### `syscalls_path`（**blocking = false**）— D9 已知缺陷

- 行内同时出现 `syscalls.c` / `sysmem.c` **且**出现 `FileNotFoundException|IOException|Exception|拒绝访问|access is denied|cannot find|no such file` → `warn`；**永不** `fail`。

### 1.5 保证边界（必须写进 SKILL.md）

> **v1.2 保证**：外设级不漏（整只外设被静默丢弃 → `main_init_present` fail）；**传 `--expect-pins` 时**引脚级也不漏（`pins_present`）。不传 `--expect-pins` 时引脚级 **不保证**（该项 `skip`，`summary.notes` 里可见）。
> **v1.2 不保证**：参数级（如 `Prescaler` 未进 `IPParameters`）。

引脚级为什么必须单独做：G474 基线本来就有 `MX_GPIO_Init`（PC13），再加一个 PB0 时，**即使 PB0 完全没进去**，外设级检查也全 pass（实测：`verdict=PASS / exit 0`）。现在传了 `--expect-pins` 就会 fail（§4.1）。不传时仍需外部断言补证：

```bash
grep -E '^Mcu\.PinsNb='  <工程>/*.ioc            # 改前 N → 改后 N+1
grep -E '^PB0\.Signal='  <工程>/*.ioc            # 应出现 GPIO_Output
grep -c '__HAL_RCC_GPIOB_CLK_ENABLE()' <工程>/Core/Src/main.c   # 基线 0 → ≥1
grep -c 'HAL_GPIO_Init(GPIOB'          <工程>/Core/Src/main.c   # 基线 0 → ≥1
```

参数级更不能拿"`.ioc` 里参数键是否齐全"当口径：真实工程 `SPI1` 的 `NSS/DataSize/CPOL/CPHA` 都不在 `.ioc`，是 CubeMX 派生默认（`stm32-digital-clock` 实证）。

## 3. `scripts/regen.sh`（T1.3）

### 3.1 选项

| 选项 | 说明 |
|---|---|
| `-e, --expect <list>` | 期望外设；默认从 `.ioc` 的 `Mcu.IP*` 推导（滤掉 `NVIC/RCC/SYS/DBGMCU`）再补 `GPIO`（G474 基线 = `GPIO`） |
| `-l, --log <path>` | 生成日志（默认 `<out>/cubemx-generate.log`） |
| `-m, --mx <script.mx>` | CubeMX 脚本（默认 `<工程>/scripts/cubemx-generate.mx`，否则 `<工程>/scripts/*.mx` 第一个） |
| `-o, --out <dir>` | 证据输出目录（默认 `${TMPDIR:-/tmp}/platform32-regen`，**故意不落工程内**） |
| **`--main-c <path>`** | 覆盖 main.c 路径（默认 `<工程>/Core/Src/main.c`） |
| **`--mxproject <path>`** | 覆盖 `.mxproject` 路径（默认 `<工程>/.mxproject`） |
| `--java` / `--cube` | 覆盖解释器/exe（默认 `$ST_CUBEMX_JRE` / `$ST_CUBEMX_EXE`，否则 `C:/ST/STM32CubeMX/...`） |
| `--timeout <sec>` | 生成超时，**最小 240**（低于自动抬到 240 并告警），默认 300 |
| `--expect-pins <PIN=SIGNAL>` | 透传核验器的引脚级检查（可重复、可逗号分隔）；不传则 `pins_present` `skip`。`regen.sh` 总会把 `--ioc "$IOC_FILE"` 一起传下去 |
| `--allow-signal <sig>` | 透传核验器；**默认已预置 `VP_RIF_VS_RIF1`**（D8），`--no-default-allow` 关闭 |
| **`--require-clean`** | `.ioc` 有未提交**内容**改动时退出 2（**默认允许脏**，见 3.2） |
| `--skip-generate` | 跳过生成，只做备份 + 核验 |
| `--dry-run` | 只打印将执行的命令，**不落盘、不宣称通过** |

**已删除**：`--allow-dirty-ioc`（默认方向反了，且不做 no-op 别名——那是语义陷阱）、`--keep-ask-for-migrate`（随注入逻辑一起删）。

环境变量：`PYTHON`（默认 `python`）、`EXPECTED_CUBEMX_VERSION`（默认 `6.18.1`）。

### 3.2 流程与判据（顺序不能变）

1. **前置检查**：工程目录、`*.ioc`、`main.c`、`.mxproject`、`.mx` 存在。
2. **git 状态**：用 `git diff HEAD --name-only -- '*.ioc'` 判脏（**不是** `git status --porcelain`）。
   - 默认：打印未提交改动清单 + 明确告知"备份已存 `<...>.ioc.bak`，失败从备份恢复，不用 git checkout"，然后继续；
   - `--require-clean`：命中脏 → **退出 2**。
   - 为什么换 `git diff`：`git status` 按工作区字节判脏，CubeMX 把 `.ioc` 写成 CRLF 会产生"内容没变但判脏"的**假阳性**（实测 `i/lf w/crlf`）；`git diff` 遵守 `.gitattributes` 的 `text=auto eol=lf`。
3. **版本戳 / 迁移提示**（只读，见 3.3）。
4. **备份**：`.ioc` → `.ioc.bak`；`.mxproject` → `.mxproject.bak`。
5. **生成**：`cd <工程> && timeout <T> <jre>/java.exe -jar <cube>.exe -q <script.mx>`，stdout+stderr → `<out>/cubemx-generate.log`。
   - **cwd 不变量**：`.mx` 里 `config load` 用相对 `.ioc`，而 CubeMX 默认 cwd 是安装目录 → 子 shell 里 `cd` 进工程根，并断言 `pwd -P == 工程根`，不等直接退出 2。
6. **KO 判据**：日志出现**整行 `KO`** → **生成阶段失败** → 回滚 → **退出 1**（见 3.4）。
7. **核验**：`verify_generation.py --project-root <工程> …` → `<out>/verify.json` + `verify.md`。
8. **失败回滚**（生成或核验失败）：从**备份**恢复 `.ioc` + `.mxproject`（`git checkout` 仅作为备份缺失时的兜底）；随后打印 `git status --porcelain -- Core/` 与 `git checkout -- Core/` 提示 —— **别让人以为回滚了就是干净了**。
9. **成功收尾**：打印证据路径 + 保证边界提醒。**不写任何 `.ioc` 字段。**

**红线**：不做**配置类**文本注入；不"智能修复"；**不改 `AskForMigrate`**。

### 3.3 `AskForMigrate`：不拦、不改，只在"真的有迁移需求"时提示

**结论以实测为准，不沿用模板文档的推测。**

- 实测：CubeMX 生成后会把 `AskForMigrate` 写回 `true`；而这个 `true` 状态**又跑过一次真生成，约 60s 正常结束、没有卡**。⇒ `true` 是稳态，**无实测卡死证据**。
- 因此：`AskForMigrate=true` 单独出现 **不告警、不拦、不改**；只有在**同时**满足「`.ioc` 的 `MxCube.Version` < 本机锁定版本」且「`=true`」时打一条 warn（真实迁移需求），文案明确写"**无实测卡死证据**"。
- 曾经的两种做法（生成前 `die 2` 硬拦 / 生成后 `ioc_field.py` 复位）都已**撤销**：前者会把稳态当故障，后者在核验之后改 `.ioc`，导致"报告证明的是 A 状态、实际交付的是 B 状态"，且未经同意改用户文件。

### 3.4 生成判据：必须查 `KO`，不能只看退出码

| 通道 | 判据 | 结果 |
|---|---|---|
| MCP（`vscode-cube-mcp`） | `returncode==0` 且无整行 `KO` | 拦得住 |
| `regen.sh`（CLI，本脚本） | `returncode==0` **且** 日志无整行 `KO` | 拦得住（v1.1 起） |

- CubeMX **退出码恒为 0**（D25），脚本层被拒也返回 0 ⇒ 只看 returncode 会**假成功**。
- 命中 KO → 打印 `[regen] 生成阶段失败：日志里有 N 行 KO（脚本层被 CubeMX 拒绝）` → 回滚 → 退出 **1**。
- 退出码 `1` 的语义：**跑过了但错了，已回滚**（生成失败与核验失败同类）；`2` 只表示"压根没跑"。
- 消息必须区分 **`[regen] 生成阶段失败`** 与 **`[regen] 核验阶段失败`**：前者是脚本层被拒，后者是生成成功但产物不对，排查方向不同。
- 边界：**"无 KO 只是必要条件，不是成功证明"** —— `set ip parameters` 会回 `OK`、无 `KO`，却静默空操作（scenario-tester 实测），那种情况只能靠 diff + G1。

### 3.5 生效白名单必须可见

`regen.sh` 启动即打印 `生效 allowlist：…`，并把同一份列表交给核验器（落 `inputs.effective_allow_signals`）。原因：直调核验器默认**空**、`regen.sh` 默认**预置 D8** —— 不留痕就会出现"同一份日志、两个入口、两种结论"。

## 5. 给消费方的引用要点

- 能力索引：`生成核验（G1 强制关卡）` → `scripts/verify_generation.py`，退出码见 §1.2。

## 6. 遗留风险与已知限制

### 6.1 日志来源红线

`--log` **必须**是 CubeMX 进程的原始 stdout/stderr。`vscode-cube-mcp` 的 `NOISE_RE`（`cubemx_mcp.py:72-104`）会整行删除 `YYYY-MM-DD HH:MM:SS,mmm [INFO|WARN|DEBUG|TRACE]` 形态的行，`Cannot map` 若落在这个形态里，**走 MCP 返回值会假阴性**；`VP_RIF_VS_RIF1` 那条噪音在 MCP 返回里也看不到。⇒ 同一份生成会因"日志从哪个入口拿"得到不同的判定基线。`regen.sh` 已直接重定向 `-q` 输出。
（S3 计划同时抓 MCP 返回与原始 stdout 比对，结论落 `docs/reports/`，T1.9 引用。）

### 6.2 Known limitations（v1.x）

| 项 | 影响 | 计划 |
|---|---|---|
| **参数级**（`Prescaler` 未进 `IPParameters`） | 外设存在、引脚也对，但某参数被静默忽略时仍 pass | **不在 v1.x 承诺**；要抓需 `.ioc` 白名单与 `main.c` 赋值交叉比对 |
| 引脚级**未传** `--expect-pins` | 此时 `pins_present` `skip`，回到"只保证外设级" | 靠 `summary.notes` 可见；S1 请显式传 `--expect-pins` |
| `.mxproject` 只判盘符路径 | UNC 不判 | 可接受（模板流不产生 UNC） |
| `.mx` 路径不做 `realpath` | 8.3 短名、符号链接未展开 | v1.2 已用 `normpath` 折叠 `..`/`.`（误报优先修），其余为可接受精度 |
| 回滚不覆盖 `Core/**` | 失败后 `Core/` 是生成结果 | 有意为之；脚本打印其状态与丢弃命令 |
| `--expect-pins` 只覆盖 `P<字母><数字>` 形式 | 虚拟引脚（`VP_*`）只做 `.ioc` 侧校验，无端口联动 | 可接受（虚拟引脚无 GPIO 端口） |
| 真生成只在 G474 验证 | F103 可跑；H723 需 FW_H7（T2.2 挂起） | — |
