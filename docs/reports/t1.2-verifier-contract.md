## 0. 一句话

`verify_generation.py` 是流水线的**强制关卡**：CubeMX 说"生成成功"不算成功，只有它报 `verdict=pass` 才算。
`regen.sh` 把"备份 → 生成前检查 → 生成 → 核验 → 失败回滚 → 字段复位"串成一条命令，任何一步不过都不把未核验的配置留在工作区。

## 1. `scripts/verify_generation.py`（v1.1.0）

### 1.1 CLI（参数名是契约，勿改）

```
python scripts/verify_generation.py \
    --log <cubeMX生成日志路径> \
    --main-c <工程/Core/Src/main.c> \
    --mxproject <工程/.mxproject> \
    --expect <外设名逗号分隔, 如 GPIO,TIM4,USART2> \
    [--project-root <工程根>] \
    [--allow-signal VP_RIF_VS_RIF1] \
    [--json-out <输出路径>] \
    [--report-md <输出路径>]
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `--log` | ✅ | CubeMX 生成日志（`regen.sh` 把 `-q` 的 stdout+stderr 全量重定向进来，约 200KB）。**必须是原始进程输出**，不能是 MCP 工具返回的过滤后文本（见 §6） |
| `--main-c` | ✅ | 生成的 `Core/Src/main.c`（**唯一**能证明外设是否真的被生成的文件） |
| `--mxproject` | ✅ | 生成的 `.mxproject`（查盘符绝对路径） |
| `--expect` | ✅ | 期望外设清单；逗号/分号/空白分隔，大小写不敏感，自动去重转大写；传空串 `""` = 不检查外设（外设类检查 `skip`） |
| `--project-root` | ❌ | 工程根目录：传入后递归扫描其下 `*.mx` 并核验绝对路径**指向哪里**；不传 → 该项 `skip` |
| `--allow-signal` | ❌ | `Cannot map` 白名单，**可重复、可逗号分隔**。命中白名单的行降级为 `warn` |
| `--json-out` | ❌ | 结构化 JSON 报告（自动建父目录） |
| `--report-md` | ❌ | Markdown 报告（含表格，适合直接贴进证据文档） |
| `--version` | ❌ | 打印 `verify_generation.py 1.1.0 (schema platform32.verify_generation/1)` |

**白名单默认值是空**（核验器必须纯净）。D8 的 `VP_RIF_VS_RIF1` 是**项目级**已知噪音，由 `regen.sh` 预置（可用 `--no-default-allow` 关）。两个入口默认值不同，所以**生效值必须落盘**：`inputs.effective_allow_signals`（见 1.3），`regen.sh` 同时把它打到 console。

### 1.2 退出码

| 码 | 含义 | 下游动作 |
|---|---|---|
| `0` | 全部通过（**允许** `warn`，如 D8/D9/占位符） | 可继续 `pio run` |
| `1` | 存在 `fail` 级问题（静默丢弃 / 路径指错地方） | **禁止**继续，回滚或修 `.ioc` |
| `2` | 输入/IO/参数错误（文件不存在、`--project-root` 不存在、报告写不了） | 修命令，**不代表配置有问题** |

### 1.3 JSON schema：`platform32.verify_generation/1`

```json
{
  "schema": "platform32.verify_generation/1",
  "verdict": "pass",
  "checks": [
    {"id": "log_cannot_map", "status": "pass", "blocking": true, "detail": "…"},
    {"id": "main_init_present", "status": "pass", "blocking": true, "detail": "GPIO → MX_GPIO_Init（exact，定义 L152）"},
    {"id": "main_init_called", "status": "pass", "blocking": true, "detail": "GPIO → MX_GPIO_Init（调用 L88）"},
    {"id": "mxproject_abs_path", "status": "pass", "blocking": true, "detail": "…"},
    {"id": "mx_script_abs_path", "status": "warn", "blocking": true, "detail": "1 处占位符未替换…scripts/cubemx-init.mx:5…"},
    {"id": "syscalls_path", "status": "pass", "blocking": false, "detail": "…"}
  ],
  "summary": {
    "errors": 0,
    "warnings": 1,
    "checked_peripherals": ["GPIO"],
    "notes": ["mx_script_abs_path: …（skip 的原因写在这里）"]
  },
  "inputs": {
    "log": "…/cubemx-generate.log",
    "main_c": "…/Core/Src/main.c",
    "mxproject": "…/.mxproject",
    "project_root": "…/g474",
    "effective_allow_signals": ["VP_RIF_VS_RIF1"]
  },
  "expect": ["GPIO"],
  "allow_signals": ["VP_RIF_VS_RIF1"],
  "tool": {"name": "verify_generation.py", "version": "1.1.0"}
}
```

字段约束（下游可依赖）：

- `checks` **恒为 6 条**，顺序固定：`log_cannot_map` → `main_init_present` → `main_init_called` → `mxproject_abs_path` → `mx_script_abs_path` → `syscalls_path`；id 不得改名。
- `status ∈ {pass, warn, fail, skip}`。
- **`blocking: bool`** —— 该检查**失败时**是否阻塞交付。它描述"检查的性质"，**不随本次 `status` 变化**：
  - 6 项里只有 `syscalls_path` 是 `false`（D9 已知缺陷，只告警）；
  - `pass` / `skip` 的检查 `blocking` 仍是 `true`。
  - ⚠️ v1.0 曾有 `level: "error"|"warning"` 字段（由 `status` 派生），导致**全 pass 的报告里 6 项都显示 `error`**，极易被误读成"有错"；v1.1 已改名为 `blocking`，`level` 字段**已删除**，请勿再消费。
- `verdict = "fail"` 当且仅当 `summary.errors > 0`；`warn` / `skip` 不影响 verdict。
- `summary.errors` = `status=fail` 条数；`summary.warnings` = `status=warn` 条数；`summary.notes` = 所有 `skip` 的原因（人能看懂"为什么某项没查"）。
- `inputs` 内路径是**绝对路径**；`project_root` 未提供时为 `null`；`effective_allow_signals` 是**生效**白名单（断言"同一份日志两个入口两种结论"的凭据）。
- 额外字段 `expect` / `allow_signals` / `tool` 留痕用，消费方可忽略。
- JSON **不含时间戳**（便于 diff 与快照比对）；时间戳只出现在 Markdown 报告里。

### 1.4 六个 check id 的判定逻辑

#### `log_cannot_map`（blocking）— 外设被静默丢弃的根因证据（D5 / H-6）

- 逐行匹配 `cannot\s+map`（大小写不敏感），记行号与原文。
- 命中行若包含任一 `--allow-signal` 值（子串、大小写不敏感）→ 该行降级；全部命中行都被降级 → `warn`，否则 `fail`。
- 日志为**空/纯空白** → `warn`（"没错误"不能靠空日志证明）。
- `OptionalMessage_ERROR` 行**不参与判定**，只在 detail 报数量：G474 最小工程必有一条 `VP_RIF_VS_RIF1` 噪音（D8），判它等于永远报错。

#### `main_init_present`（blocking）— 期望外设是否真的有初始化函数**定义**

- 先对 `main.c` 做**注释/字符串剥离**（保留换行、行号不变）再解析，避免把注释里的"死定义"当成定义。
- 判定为定义：`MX_<...>_Init(...)` 后跟 `{`；跟 `;` 的是原型声明，不算。
- 外设 → 符号的**容错匹配**（顺序即优先级，大小写不敏感）：
  1. 精确 `MX_<PERIPH>_Init`（`GPIO` → `MX_GPIO_Init`）；
  2. 功能后缀 `MX_<PERIPH>_<FUNC>_Init`，`FUNC ∈ {UART, USART, LPUART, TIM, SPI, I2C, ADC, DAC, CAN, Device, Host, SD, ETH, SAI, I2S, RTC, FLASH, USB, COMP, OPAMP, CRC, RNG, HCD}`（`USART2` → `MX_USART2_UART_Init`、`USB` → `MX_USB_Device_Init`）；
  3. 兜底：`MX_<PERIPH>_<TOKEN>_Init` 且**唯一**命中（标 `fuzzy`）；多候选报歧义、判缺失。
- **不做子树误匹配**：`--expect TIM` 不会匹配 `MX_TIM4_Init`（否则"少配一个定时器"会被漏报）。
- detail 必须写出实际符号名 + 匹配方式 + 定义行号。
- `--expect ""` → `skip`。

#### `main_init_called`（blocking）— 初始化函数是否在 `main()` 体内**被调用**

- 大括号配平定位 `int main(void) { … }`；找不到 `main` → `fail`。
- 体内搜 `\b<symbol>\s*\(`；注释已剥离，`/* MX_TIM4_Init(); */` **不算调用**。
- 只核验"确实有定义"的符号（缺定义的已在上一项报过）；一个定义都没有 → `skip`（不重复报同一根因）。

#### `mxproject_abs_path`（blocking）— 工程文件可移植性（TOOLING §3.2）

- 逐行匹配 `(?<![A-Za-z0-9])[A-Za-z]:[\\/]`；命中即 `fail`，报行号与截短内容。
- 反向断言挡掉 `http://`、`file:///` 这类伪盘符（有单测）。
- 只判盘符路径，不判 UNC 与相对路径。

#### `mx_script_abs_path`（blocking）— CubeMX 脚本的绝对路径**指向哪里**

**这是 `mxproject_abs_path` 的姊妹检查，不是"有盘符就 fail"。** 依据模板 `TEMPLATE-PLACEHOLDERS.md` A1：**CubeMX 脚本不支持变量，`project path` 必须硬写绝对路径** —— 所以"存在绝对路径"是**合规**的，真正的缺陷是"指向别处"。

扫描范围：`<--project-root>/**/*.mx`（跳过 `.git` / `.pio` / `Drivers` / `Middlewares` / `node_modules` / `.venv` / `__pycache__`）。

| 命中内容 | status | 含义 |
|---|---|---|
| `__PROJECT_DIR__` / `__PROJECT_NAME__` 等 `__[A-Z_]+__` 占位符 | `warn` | 脚本未配置，直接跑会失败（`cubemx-init.mx` 的初始状态） |
| 归一化后 **== 本工程根**（或其内部） | `pass` | 自指，A1 的正常形态 |
| 归一化后是本工程根的**上级目录** | `warn` | 需配合 `project name` 才落对目录，人工确认 |
| 归一化后**指向别处** | `fail` | 生成会写进另一个工程；克隆到新机器必踩 |
| 无盘符路径 / 无 `.mx` / 未传 `--project-root` | `pass` / `skip` | 不适用 |

- 归一化：`/`→`\`、压缩重复分隔符、去尾分隔符、`casefold()`。**不做 `realpath`**（路径常指向另一台机器，解析会失败），8.3 短名与符号链接不展开 —— 已知边界。
- detail 格式：`相对路径:行号: 片段（in_comment=true|false）`，片段截断 120 字符。
- **注释里的绝对路径照样报**（写死在注释里同样是运维陷阱），只用 `in_comment` 标记供人判断。
- 占位符优先于路径比较（占位符是"未配置"的失败前兆）。
- 这条检查要回答的问题是：**"这份脚本在当前这台机器、这个位置，还对不对"** —— 不是代码风格检查。

#### `syscalls_path`（**blocking = false**）— D9 已知缺陷

- 行内同时出现 `syscalls.c` / `sysmem.c` **且**出现 `FileNotFoundException|IOException|Exception|拒绝访问|access is denied|cannot find|no such file` → `warn`。
- **永不** `fail`：这两份 newlib 桩改动极少，叠加路径是 CubeMX 缺陷，不该让流水线卡死（调研报告 §7）。

### 1.5 保证边界（必须写进 SKILL.md，否则会被误用）

本核验器的粒度是**外设级**：它抓的是"**整只外设**被静默丢弃"（`MX_TIM4_Init` 消失，H-6）。

**`verdict=pass` 不代表引脚级增量已经生效。** 例：G474 基线本来就有 `MX_GPIO_Init`（PC13），
再加一个 PB0 输出时，5/6 项检查在"PB0 完全没加进去"的情况下**依然全 pass** —— 因为 `GPIO`
这个外设早就在了。这正是调研报告 C2 想防的"幻觉"，只是换了个层级。

引脚级改动的判别力要另加断言（基线为 0 才有判别力），例如：

```bash
grep -E '^Mcu\.PinsNb='  <工程>/*.ioc            # 改前 N → 改后 N+1
grep -E '^PB0\.Signal='  <工程>/*.ioc            # 应出现 GPIO_Output
grep -c '__HAL_RCC_GPIOB_CLK_ENABLE()' <工程>/Core/Src/main.c   # 基线 0 → ≥1
grep -c 'HAL_GPIO_Init(GPIOB'          <工程>/Core/Src/main.c   # 基线 0 → ≥1
```

`--expect-pin` 这类引脚级检查属 **v2 待评估**（需先改契约再实现）。

### 2.1 `scripts/ioc_backup.py`（备份 / 还原，git 之外的第二道保险）

```
python scripts/ioc_backup.py --project <工程目录> [--list] [--restore] [--json-out <path>]
```

| 行为 | 说明 |
|---|---|
| 默认（备份） | 顶层每个 `*.ioc` → `<name>.ioc.bak`；临时文件 + `os.replace` 原子落盘；记录字节数与 `sha256` |

| `--restore` | 从 `<name>.ioc.bak` 还原（非 git 工程的回滚通道） |
| `--json-out` | schema `platform32.ioc_backup/1`，含 `files[].sha256` —— **回滚"确实还原了原件"的凭据** |

退出码：`0` / `1`（未找到 `.ioc`，或还原时缺 `.bak`）/ `2`（参数或 IO）。
`.ioc.bak` 已被模板 `.gitignore` 的 `*.ioc.bak` 忽略，不污染 `git status`。

### 2.2 `scripts/ioc_field.py`（单键读写，供 `regen.sh` 复位弹窗开关）

```

```

- 只做 `key=value` 单行替换，**不新增/删除行**；保留原行尾（CRLF/LF）与文件末尾换行；原子写。
- 值已经是目标值时**不写盘**（保持 mtime，避免无意义 diff）。
- 键不存在或多行同名 → 退出码 `1`（拒绝猜测）；文件不存在 → `2`。

## 3. `scripts/regen.sh`（T1.3）

### 3.1 选项

| 选项 | 说明 |
|---|---|
| `-e, --expect <list>` | 期望外设；**默认从 `.ioc` 的 `Mcu.IP*` 推导**（滤掉 `NVIC/RCC/SYS/DBGMCU`）再补 `GPIO`（G474 基线推导结果 = `GPIO`） |
| `-l, --log <path>` | 生成日志路径（默认 `<out>/cubemx-generate.log`） |
| `-m, --mx <script.mx>` | CubeMX 脚本（默认 `<工程>/scripts/cubemx-generate.mx`，找不到则在 `<工程>/scripts/*.mx` 取第一个） |
| `-o, --out <dir>` | 证据输出目录（默认 `${TMPDIR:-/tmp}/platform32-regen`，**故意不落工程内**，避免脏 `git status`） |
| `--java` / `--cube` | 覆盖解释器/exe（默认 `$ST_CUBEMX_JRE` / `$ST_CUBEMX_EXE`，否则 `C:/ST/STM32CubeMX/...`） |
| `--timeout <sec>` | 生成超时，**最小 240**（低于自动抬到 240 并告警）；默认 300 |
| `--allow-signal <sig>` | 透传核验器；**默认已预置 `VP_RIF_VS_RIF1`**（D8），`--no-default-allow` 关闭 |
| `--keep-ask-for-migrate` | 生成成功后**不**把 `AskForMigrate` 复位为 `false`（观察 CubeMX 原始行为时用） |
| `--allow-dirty-ioc` | 允许 `.ioc` 处于未提交改动时继续（默认拒绝） |
| `--skip-generate` | 跳过生成，只做备份 + 核验 |
| `--dry-run` | 只打印将执行的命令，不落盘 |

环境变量：`PYTHON`（默认 `python`）、`EXPECTED_CUBEMX_VERSION`（默认 `6.18.1`，只用于版本戳告警）。

### 3.2 流程与安全语义（顺序不能变）

1. **前置检查**：工程目录存在、有 `*.ioc`、`Core/Src/main.c` 与 `.mxproject` 已存在、`.mx` 存在。
2. **git 干净检查**：`.ioc` 有未提交改动 → **退出 2**，并直接打印下一步命令（`--allow-dirty-ioc` 或 `git stash`）。理由：回滚是 `git checkout`，会丢用户改动（调研报告 C5）。
3. **`AskForMigrate` 硬拦（生成前，退出 2）** —— 见 3.3。
4. **版本戳告警**：`MxCube.Version` ≠ 锁定版本 → 只 `warn`（P2 提交卫生，不是正确性门）。
5. **备份**：`ioc_backup.py` → `<工程>/<name>.ioc.bak` + `<out>/ioc-backup.json`。
6. **生成**：`cd <工程> && timeout <T> <jre>/java.exe -jar <cube>.exe -q <script.mx>`，stdout+stderr 全量进 `<out>/cubemx-generate.log`。
7. **核验**：`verify_generation.py --project-root <工程> …` → `<out>/verify.json` + `verify.md`。
8. **失败回滚**（生成失败或核验非 0）：`git checkout -- '*.ioc'`，已入库的 `.mxproject` 一并 checkout；非 git 工程退化为 `ioc_backup.py --restore`；回滚后打印 `git status`。
9. **成功收尾**：把 `AskForMigrate` 复位为 `false`（见 3.3），打印证据路径 + "保证边界"提醒。

**红线**：不做**配置类**文本注入（引脚/外设/参数一律走 CubeMX CLI `set` 或 MCP）；不"智能修复"配置——失败就是回滚 + 报错。

### 3.3 `AskForMigrate`：为什么是前置硬拦，而不是一个 check

`ProjectManager.AskForMigrate=true` 的危害发生在**生成时**：`-q` 非交互模式会停在迁移对话框，
一直阻塞到超时（300s 白等），而且**从"超时"这个现象看不出根因**。等生成完再核验，人已经白等了。
所以它必须是 `regen.sh` 的**生成前**检查（退出 2，不进生成步骤），**不占 check id**、不影响 JSON schema。

- **生成前**：`grep -qE '^ProjectManager.AskForMigrate=true'` 命中 → 退出 2，打印两条处置（GUI 重存 / `ioc_field.py` 改单行）。
- **生成成功后**：CubeMX 每次生成都会把它写回 `true`（TOOLING §3.3 / D7），所以成功路径必须**复位为 `false`**（`ioc_field.py` 精确改单行，证据 `<out>/ioc-normalization.json`），否则第二次生成必被同一前置拦死。
- `--keep-ask-for-migrate` 可跳过复位（想观察 CubeMX 原始行为时用）。
- 实测：真实工程 `stm32-digital-clock.ioc` 就是 `true`（由 CubeMX 6.17.0 生成），**不是 G474 特例**。

### 3.4 cwd 不变量（CubeMX 的隐形坑）

`cubemx-generate.mx` 用**相对** `.ioc` 路径（`config load stm32-g474-template.ioc`），而 CubeMX 的默认
cwd 是**安装目录**。所以：**调 CubeMX 时 cwd 必须是工程根**。`regen.sh` 在子 shell 里 `cd` 进工程根，
并在执行前断言 `pwd -P == 工程根`，不满足直接退出 2（并把 cwd 打进日志）。

### 3.5 生效白名单必须可见

`regen.sh` 在启动时打印 `生效 allowlist：…`，并把同一份列表交给核验器（落进
`inputs.effective_allow_signals`）。原因：直调核验器默认**空**、`regen.sh` 默认**预置 D8** ——
不显式留痕就会出现"同一份日志、两个入口、两种结论"。

## 6. 遗留风险与边界

| 项 | 影响 | 现状 |
|---|---|---|
| 参数级漏配抓不到 | 外设存在但某参数被静默忽略（如 `Prescaler` 没进 `IPParameters`）时仍 pass | 已知边界。`.ioc` 白名单与 `main.c` 赋值做交叉比对属 v2；**不要**用"参数键是否齐全"当口径——真实工程里 `SPI1` 的 `NSS/DataSize/CPOL/CPHA` 都不在 `.ioc`，是 CubeMX 派生默认（`stm32-digital-clock` 实证） |
| 引脚级增量抓不到 | S1 类"多一个 PB0"的改动在核验里是真空 PASS | 已知边界，见 §1.5；`--expect-pin` 属 v2 |
| `.mxproject` 只判盘符路径 | UNC（`\\server\share`）不判 | 可接受；模板流不会产生 UNC |
| `.mx` 路径不做 `realpath` | 8.3 短名、符号链接、大小写变体可能误判 | 归一化 + casefold 已覆盖常见情形 |
| 回滚不覆盖 `Core/**` | 失败后 `Core/` 是本次生成结果 | 与 T1.3 DoD 一致 |
| `.ioc` 复位是唯一写盘例外 | 与"不做文本注入"红线相邻 | 只改 `ProjectManager.AskForMigrate` 单行（弹窗开关，非配置项），保留 CRLF，可用 `--keep-ask-for-migrate` 关闭 |
| 日志来源必须是原始进程输出 | MCP 返回文本会被上游 `NOISE_RE` 过滤（`^\d{4}-.. [INFO/WARN]` 整行删除），可能把 `Cannot map` 吃掉 | `regen.sh` 已直接重定向 `-q` 的 stdout/stderr；**不要**把 MCP 工具返回值当 `--log` |
| 真生成只在 G474 验证 | F103 可跑；H723 需先装 FW_H7（T2.2 挂起） | 见 TASKBOARD |
| `.gitattributes` 缺 `*.sh text eol=lf` | 在 `core.autocrlf=true` 的机器上 clone 后 `regen.sh` 会因 CRLF 跑不起来 | 建议由 `skill-author` 在 `.gitattributes` 补一行（不属本次改动范围） |
