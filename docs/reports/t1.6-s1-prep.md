### `scripts/cubemx-generate.mx` ← **改完 `.ioc` 后重生成代码就用它**


| `project path __PROJECT_DIR__`（占位符未替换） | 从裸 MCU 建工程会失败（路径非法） | **warn**：占位符未替换。但**只影响 `cubemx-init.mx`**，不影响 `cubemx-generate.mx` 的重生成流程 → 对 `regen.sh` 属无害 |
| `project path D:\...\<本工程自己的路径>` | 本机**正确**，换机/换盘符即坏 | **warn（可移植性）**，非 fail：本机功能正确 |
| `project path D:\...\<别的工程的路径>` | 指向错误目录，本机就会写错地方 | **fail** |

**正确结论**：这不是"漏检导致的错误配置"，而是"**漏检的可移植性风险**"，且**模板本身就有意要求用户填绝对路径**（因为 CubeMX 脚本不支持变量）。所以：
- 严重度从 🔴 → 🟡
- 检查应为 **warning 级 + 三态判别**（占位符未替换 / 本机自指 / 指向别处），**不能一刀切 fail**，否则会对**每个正确填了 A1 的模板副本假阳性**

# 第二部分（c）：S1 改动方案设计

## 6. 选引脚：**PB0**（主推荐）

### 6.1 候选对比

板级事实（`docs/BOARD-penguins-g474.md` §2）：

| 候选 | 板上角色 | 排除理由 / 保留理由 |
|---|---|---|
| PC13 | **LED_R**（已占用，模板默认闪它） | ❌ 已占用 |
| PC14 / PC15 | LED_G / LED_B | ⚠️ **备份域引脚，驱动能力弱**（板级文档明示"只适合指示灯，不要输出高速信号"），且与 LSE `OSC32_IN/OUT` 复用 → 命中 lead 的"避开板级特殊功能"。**且它们需要额外注意备份域语义**，会把 S1 的变量从 1 个变成 3 个 |
| PC0–PC3 | KEY_S1…S4（输入，板上有外部上拉） | ❌ 板级功能已占用；配成输出会与外部上拉对打 |
| PA13 / PA14 | SWD | ❌ 绝对禁止（会把自己的调试口关掉） |
| PF0 / PF1 | HSE 24 MHz 晶振 | ❌ 模拟/时钟专用 |
| **PB0** | **板上未分配** | ✅ **选它** |

### 6.2 选 PB0 的理由（4 条）

1. **板上未占用**：`BOARD-penguins-g474.md` 的引脚表里没有 PB0，与 LED/按键/晶振/SWD 全无冲突。
2. **不是备份域**：普通 GPIOB 引脚，无 PC13/14/15 那样的弱驱动与 OSC32 复用限制。
3. **不触碰时钟/电源语义**：加它**不需要** EnableBkUpAccess、不需要改 RCC、不需要改电压档 → **改动面最小**，符合 S1"只验证链路"的目的。
4. **LQFP100 上确定存在**：PB0 在 G474VET6 的 LQFP100 封装上可用（GPIOB 在 100 脚封装是完整的 16 位）。

### 6.3 反面权衡（诚实记录）

PB0 在板上**没有 LED**，所以将来 L5 实板验证时**无法用肉眼观察**。若后续要 S1 升级成 L5 可观察，需改用 **PC14 (LED_G)** ——代价是要接受备份域弱驱动 + OSC32 复用。**本方案优先"改动最小、可判定"，不优先"将来可肉眼验证"**，因为 S1 的 DoD 只到 L3（`pio run`）。

> 若 lead 更看重"将来 L5 能肉眼看到"，请指示改 PC14，我改方案（其余步骤不变，只改引脚名）。

### 6.4 改动后的即时校验点（用来判断"是否越界"）

| 指标 | before | 预期 after | 若不符说明什么 |
|---|---|---|---|
| `Mcu.PinsNb` | **5** | **6** | 没变 → 引脚没加进去（白名单/`set pin` 失败） |
| `Mcu.IPNb` | **3** | **3（应不变）** | 变成 4 → 顺带引入了 IP 级外设 → **越界，回退** |
| `Mcu.Pin5` | 不存在 | `PB0` | — |
| `main.c` 里 `__HAL_RCC_GPIOB_CLK_ENABLE()` | 无 | **有** | 没有 → 生成了但没生效 |
| `main.c` 里 `HAL_GPIO_Init(GPIOB` | 无 | **有** | 同上 |

> `Mcu.IPNb` 保持 3 这一点有**现成实证**：模板当前 PC13 就是 `GPIO_Output`，而 `Mcu.IPNb=3`（NVIC+RCC+SYS）→ **GPIO 不计入 `Mcu.IP*`**。所以"IPNb 不变"是可预期的，不是猜测。

## 9.5 🔴 S1 的证据有效性缺口：核验器对 GPIO 级改动是**真空 PASS**（已实测）

> **⚠️ 本节的断言清单已被干跑结果修订。最终版见 `docs/reports/t1.6-s1-dryrun.md` §7（P1–P7）。**
> 主要修订：原 P2「`Mcu.Pin5=PB0`」错误 —— 实测 CubeMX 会把新引脚插到 `Mcu.Pin1` 并**重排后续索引**，故断言必须改为**存在性匹配** `^Mcu\.Pin[0-9]+=PB0$`，不能绑索引。另新增 P6（`Mcu.IPNb` 保持 3）与 P7（实质改动仅 2 文件，用 `git diff --numstat` 判）。

### 9.5.1 实测

对**完全未改动的** G474 基线（`Mcu.PinsNb=5`、`main.c` 里 `GPIOB` 出现 **0** 次）跑：

```bash
python scripts/verify_generation.py --log <synth> \
  --main-c testbeds/template-mcu-STM32G474-series/Core/Src/main.c \
  --mxproject testbeds/template-mcu-STM32G474-series/.mxproject \
  --expect GPIO --allow-signal VP_RIF_VS_RIF1
```

结果：

```
verdict=PASS errors=0 warnings=0 expect=GPIO
  [pass] main_init_present   全部 1 个期望外设都有初始化函数定义：GPIO → MX_GPIO_Init（exact，定义 L152）
  [pass] main_init_called    全部 1 个初始化函数都在 main() 内被调用：GPIO → MX_GPIO_Init（调用 L88）
  ...（其余 3 项全 pass）
EXIT=0
```

**即：PB0 一个都还没加，核验器已经 PASS 了。**

### 9.5.2 根因：核验粒度是"外设级"，不是"引脚级"

`main_init_present` 的判定是「`MX_<IP>_Init()` 是否存在」，而 `GPIO` 这个"外设"在模板里**本来就有**（PC13 一直在用 `MX_GPIO_Init`）。所以：

> **S1 加的 PB0 是"已存在外设内部的引脚增量"，核验器的任何一个 check 都不会因此变红或变绿。**
> **S1 的「核验 JSON pass」若只引用这个 PASS，等于零证据。**

这不是核验器的 bug —— 它的设计目标是抓 **D5/H-6「外设被静默丢弃」**（`MX_TIM4_Init` 整个消失），那它抓得对。**是 S1 的验收口径需要补一层**。

### 9.5.3 我打算怎么补（S1 的 pin 级断言，不依赖 `scripts/`）

在 S1 证据里额外落一份 **pin 级证据链**，3 条全过才算 S1 通过：

| # | 断言 | 命令 | 期望 |
|---|---|---|---|
| P1 | `.ioc` 里出现了新引脚 | `grep -E '^Mcu\.PinsNb=' *.ioc` / `grep -E '^PB0\.Signal=' *.ioc` | `Mcu.PinsNb=6`、`PB0.Signal=GPIO_Output` |
| P2 | `.ioc` 里 `Mcu.Pin5` 指向 PB0 | `grep -E '^Mcu\.Pin5=' *.ioc` | `Mcu.Pin5=PB0` |
| P3 | `main.c` 里真的初始化了 GPIOB | `grep -c '__HAL_RCC_GPIOB_CLK_ENABLE()' Core/Src/main.c` / `grep -c 'HAL_GPIO_Init(GPIOB' Core/Src/main.c` | 各 ≥ 1（基线均为 **0**） |

> P3 的"基线为 0"是这套断言的**判别力来源**：改动前 0，改动后 ≥1 → 能真正区分"加进去了"与"没加进去"。已实测基线 `grep -c GPIOB main.c` = **0**（见 9.5.1）。

### 9.5.4 建议（转 verifier-dev / skill-author，非我职责）

1. **核验器**：可考虑增一个 `pin_present` 可选检查（`--expect-pin PB0=GPIO_Output`，读 `.ioc` 的 `<pin>.Signal` + 校验 `main.c` 有对应 `GPIOx` 使能）。**属增强，不是 S1 阻塞**——S1 我用 9.5.3 的外部断言顶住。
2. **SKILL.md 必须写明**：`verify_generation.py` 的保证边界是**外设级**；**GPIO/Label/PinState 这类引脚级改动它看不见**，必须人工或用 pin 级断言补核。否则使用者会误以为"核验 PASS = 改动生效"，这正是调研报告 C2 想防的那类幻觉，只是换了个层级。
3. **S1 的 DoD 表述建议修正**：把「核验 JSON pass」改为「核验 JSON pass **且** pin 级断言 P1–P3 全过」——否则 DoD 可被真空满足。
