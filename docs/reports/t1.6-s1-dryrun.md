**逐条回答 env-agent 报告 §7 的两个待验证项：**

### Q1：`set pin PBx GPIO_Output` 是否自动补 `PBx.GPIOParameters` 白名单？→ **不会**

`.ioc` 实际新增的只有两行：

```ini
+PB0.Locked=true
+PB0.Signal=GPIO_Output
```

**没有** `PB0.GPIOParameters`。

判断：**对"纯推挽输出"不构成缺陷**。对照 TOOLING §3.5 —— 白名单只在**要设参数**时才必须成对出现（`GPIOParameters=PinState` + `PinState=GPIO_PIN_SET` 才让初始电平生效）。本场景不设参数，故无白名单也不会被静默丢弃，`main.c` 里确实生成了完整的 `GPIO_InitStruct`（见 §4）。**但结论要说准**：`set pin` 本身**不做**白名单补丁 → 若将来要设 `PinState`/`GPIO_Label`，必须**显式**再发 `set gpio parameters`，不能指望它自动补。

### Q2：`set gpio parameters PBx PinState=GPIO_PIN_SET` 语法是否被 6.18 接受？→ **本次未测**

按设计（方案 A，变量最少）刻意绕开了它。仍属未验证项。**若 lead 裁决 D-b 要"让 PB0 有初始电平"，才需补这一步实测。**

## 5. 🔴 关键发现：`git status` 会说 8 个文件改了，`git diff` 只有 2 个

### 5.1 现象

```
git status --porcelain  →  8 个 M
  M .mxproject
  M Core/Inc/main.h
  M Core/Inc/stm32g4xx_hal_conf.h
  M Core/Inc/stm32g4xx_it.h
  M Core/Src/main.c
  M Core/Src/stm32g4xx_hal_msp.c
  M Core/Src/stm32g4xx_it.c
  M stm32-g474-template.ioc

git diff --numstat      →  只有 2 个有实质内容变更
  11  0  Core/Src/main.c
   9  6  stm32-g474-template.ioc
```

### 5.2 根因（`git ls-files --eol` 权威证据）

```
i/lf  w/crlf  attr/text=auto eol=lf   .mxproject
i/lf  w/crlf  attr/text=auto eol=lf   Core/Inc/main.h
i/lf  w/crlf  attr/text=auto eol=lf   Core/Inc/stm32g4xx_hal_conf.h
i/lf  w/crlf  attr/text=auto eol=lf   Core/Src/main.c
i/lf  w/crlf  attr/text=auto eol=lf   Core/Src/stm32g4xx_hal_msp.c
i/lf  w/lf    attr/text=auto eol=lf   Core/Src/syscalls.c      ← 未被 CubeMX 重写
i/lf  w/lf    attr/text=auto eol=lf   Core/Src/sysmem.c        ← 未被 CubeMX 重写
i/lf  w/crlf  attr/text=auto eol=lf   stm32-g474-template.ioc
```

CubeMX 把它们**写成了 CRLF**（`w/crlf`），index 是 LF；`.gitattributes` 的 `* text=auto eol=lf` 在 `diff` 时归一化 → **内容 diff 为空**，但 `status` 仍因工作区字节不同而标 `M`。

这正是模板 `.gitattributes` 注释里写明的预期行为（"CubeMX 在 Windows 下仍可能写回 CRLF；text 属性在 add/status/diff 时归一化，不会仅因 LF/CRLF 的差别产生内容 diff"）。

### 5.3 对 S1 DoD 的影响（**必须写进 SKILL.md**）

S1 的 DoD 是「diff 仅含预期文件」。若按 `git status` 判，会看到 **8 个文件**，其中 6 个是"看起来改了、其实内容一致"的假阳性 → **会被误判成越界**。

**正确判定口径**：`git diff --numstat`（或 `--stat`）—— 只有它反映实质内容变更。`git status` 只能用来发现"有文件被工具碰过"，不能用来判定"改了哪些内容"。

### 5.4 附带确认：TOOLING §3.4 得到实测印证

`syscalls.c` / `sysmem.c` 的 `w/lf` 证明 **CubeMX 确实没有重写这两个文件**（叠加路径 bug），与 TOOLING §3.4 一致。它们**没有出现在 `git status` 的 8 个 M 里** —— 这条对我原设计里"若不出现 diff 说明异常"的判断需要修正为：**它们根本不进入 status，不是"没 diff"而是"压根没被写"**。
