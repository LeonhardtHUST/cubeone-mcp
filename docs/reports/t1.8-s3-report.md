### 4.2 🔴 更正：`Cannot map` 经 MCP 通道**必然假阴性**（本报告初版结论相反，已撤销）

**初版错误结论（已作废）**：我写过"`Cannot map` 级别是 `[INFO]` 而非 `[WARN]`，所以 `NOISE_RE` 不会吞掉它，MCP 假阴性风险不成立"。
**这个结论是错的，且反在安全红线上。** 由 lead 指出后我自行复核源码并实测复现，结论如下。

#### 事实 1：`NOISE_RE` 的级别集合**包含 `INFO`**

`C:\Users\Leon\AppData\Roaming\uv\tools\vscode-cube-mcp\Lib\site-packages\cubemx_mcp.py:72-77`：

```python
NOISE_RE = re.compile(
    r"^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2},\d{3} \[(INFO|WARN|DEBUG|TRACE)\]|"
    r"^(Picked up|log4j[: ]|[A-Z][a-z]{2} \d{2}, \d{4} \d{1,2}:\d{2}:\d{2} (AM|PM)|"
    r"WARNING: Could not open|Configure log4j|Cannot load)",
    re.MULTILINE,
)
```

级��集合是 **`INFO|WARN|DEBUG|TRACE`** → **`INFO` 在里面，`ERROR` 不在**。而我实测的 `Cannot map` 行级别正是 **`[INFO]`**。

#### 事实 2：使用方式是**整行丢弃**，不是削前缀

`cubemx_mcp.py:96-104`：

```python
def _cleanup(raw: str) -> str:
    lines = []
    for ln in raw.splitlines():
        if NOISE_RE.match(ln):
            continue          # ← 命中即整行跳过
        s = ln.strip()
        if s:
            lines.append(s)
    return "\n".join(lines)
```

→ `NOISE_RE.match(ln)` 命中 ⇒ **`continue` 整行跳过**，不是 `sub('')` 削前缀。

#### 事实 3：用**本次真实日志**跑一遍 `_cleanup`，`Cannot map` 完全消失

我抽出源码里的 `NOISE_RE` 与 `_cleanup` 原样执行，输入是三行真实输出：

```
2026-11-03 12:33:47,866 [INFO] ImportTextPane:234 - (OptionalMessage_ERROR) Cannot map signal (VP_TIM4_VS_ClockSourceINT) on pin (VP_TIM4_VS_ClockSourceINT)
2026-11-03 12:33:47,900 [INFO] ProjectChoiceTab:3888 - New firmware version: STM32Cube FW_G4 V1.6.3
OK
```

`_cleanup()` 输出：

```
'OK'
```

**→ 两行 `[INFO]` 全被删，只剩 `OK`。`Cannot map` 一个字都没留下。**

#### 结论（修正后）

> `Cannot map signal` 的级别为 **`[INFO]`**，**恰好落在 `NOISE_RE` 的过滤集合 `(INFO|WARN|DEBUG|TRACE)` 内**，而 `_cleanup()` 对命中行是**整行丢弃** ⇒ **经 MCP 通道读取该行必然丢失，`log_cannot_map` 会恒 `pass`（100% 假阴性）。**
> **这是 `--log` 必须使用 `-q` 原始 stdout 重定向的第二个、也是更硬的理由**（第一个理由是原始日志信息更全）。

**风险等级说明**：这比"没有守卫"更危险 —— 使用者以为有 D5 守卫，实际守卫被上游净化层静默掐断。**任何把 `cubemx_generate` 的 MCP 返回值直接喂给核验器的设计都必须禁止。**

> **教训（我自己的）**：我上一版只看了 `NOISE_RE` 的**正则字面**就下了"级别不在集合内所以安全"的判断，**没有查它怎么被使用**（`match` + `continue` 是整行丢，不是 `sub`）。正则能匹配 ≠ 会删行；反过来也一样。判断"某条日志会不会丢"，必须查**消费端代码路径**，不能只看过滤规则本身。

## 4.2b 🔴 新发现（真 bug）：核验器对真实形态**抽取信号名失败**，抽出的是字面量 `'signal'`

### 现象

核验器在 S3(b) 的 detail 里写的是 `L321: signal ← 2026-11-03 … Cannot map signal (VP_TIM4_VS_ClockSourceINT) …`。
我最初把这当成输出截断，**实测后确认不是** —— 它真的把 **`signal` 这个词**当成了信号名。

### 实测（直接执行核验器源码里的两个抽取正则）

| 输入 | `_QUOTED_SIGNAL_RE` | `_BARE_SIGNAL_RE` |
|---|---|---|
| **我的真实样本**：`Cannot map signal (VP_TIM4_VS_ClockSourceINT) on pin (…)` | `None` | **`'signal'`** ❌ |
| 构造样本（**非实测**，仅测正则鲁棒性）：`Cannot map "S_<IPX>_CH1" on pin PXX` | 正确取出引号内名称 ✅ | `None` |
| 构造样本（**非实测**）：`Cannot map signal S_<IPX>_CH1 on pin PXX` | `None` | 正确取出裸名 ✅ |

### 根因

```python
_QUOTED_SIGNAL_RE = re.compile(r"[\"'`]([A-Za-z0-9_./\\-]+)[\"'`]")
_BARE_SIGNAL_RE   = re.compile(r"cannot\s+map\s+(?:signal\s+)?([A-Za-z0-9_]+)", re.IGNORECASE)
```

真实形态里 `signal` 后面紧跟 `(`，所以：
1. `_QUOTED_SIGNAL_RE` 要求引号 → 真实形态无引号 → **不命中**
2. `_BARE_SIGNAL_RE` 的 `(?:signal\s+)?` 先吃掉 `signal `，随后 `([A-Za-z0-9_]+)` 撞上 `(` 无法匹配 → **正则回溯**，让可选组匹配空，于是 `([A-Za-z0-9_]+)` 捕获到 **`signal`** 这个词

### 影响（比"提取不到"更糟）

| 场景 | 后果 |
|---|---|
| 用户想把一个**已知噪音**信号加进 `--allow-signal` | 永远匹配不上（抽取值是 `signal`）→ **合法的白名单失效，产生假 FAIL** |
| 有人把 `signal` 加进 `--allow-signal`（看起来无害） | **所有**圆括号形态的 `Cannot map` 都被静默放行 → **假 PASS**，D5 守卫被绕过 |
| 本次 S1/S3 的结论 | **不受影响**：S3(b) 本就需要 FAIL，`signal` 不在白名单 → 判 fail 是正确结果（属"错得碰巧对"）；S1 日志无 `Cannot map` |

### 建议修法（给 verifier-dev）

把"圆括号形态"作为**独立分支**并排除字面量 `signal`：

```python
_SIGNAL_PATTERNS = (
    re.compile(r"cannot\s+map\s+signal\s*\(([^)]+)\)", re.I),   # 真实形态（首选）
    re.compile(r"[\"'`]([A-Za-z0-9_./\\-]+)[\"'`]"),             # 引号形态
    re.compile(r"cannot\s+map\s+(?:signal\s+)?([A-Za-z0-9_]+)", re.I),  # 裸名（兜底）
)
# 兜底命中后必须排除：if name.lower() == "signal": 视为未提取到
```

### 为什么这条重要

`log_cannot_map` 的**判定**（有没有 `Cannot map`）是对的（`cannot\s+map` 子串匹配很稳，四种形态全命中，且正确地**不**误命中 `cannot be retrieved` 噪音）。
**错的只有"抽取信号名"这一步**，而这一步**恰好是 `--allow-signal` 白名单的唯一依据** —— 白名单是 G1 在真实工程里能不能用的关键（否则每个已知噪音都会挡住流水线）。
